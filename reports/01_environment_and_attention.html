01 · 同一份历史位置名单，为什么取 K/V 的写法能相差 25 倍？¶

本课研究生成一个 token 时，某一层读取历史 K/V 的这段计算：如果先选出少量历史位置，再只对这些位置做注意力，省下的计算能否抵消选位置、取数据的额外时间？

实验先把这段计算单独拿出来。程序直接构造当前查询和历史数组，不输入文字，也不运行 Qwen。下面两组测量分别检查其中的操作，以及操作连起来后的总成本；项目记录把它们编号为 G0 和 G1a。

第一组：把“打分、选位置、取 K/V”拆开测（G0）¶

以 32K 档为例，程序为每个 K/V 组准备 32,768 行 K 和 32,768 行 V，每行 128 个数，共 8 个组。另外随机生成每个历史位置的 32 维索引向量，以及当前查询的 32 维索引向量，供选择位置使用。这些都是测试数组，没有对应的文章或问题；这一组里的 K 填为 0.01，V 填为 0.02。

接下来分别计时：

  1. 给历史位置打分。 当前查询的索引向量与全部历史索引向量做点积，得到每组 32,768 个分数。这里测的是这次打分，不含生成索引向量的投影。
  2. 选出位置。 从已准备好的分数中取最高的 1,024 个，输出每组的位置名单。
  3. 按名单取 K/V。 用已准备好的同一份名单，从 K 和 V 各取出 1,024 行，得到后续注意力可使用的两份小数组。比较不同取行写法时，K/V 和位置名单都相同，计时只包含取 K、取 V，不包含前两步。

标题中的“相差 25 倍”就发生在第三项：取的是同样的行，程序的取行写法不同，耗时却不同。G0 还把这三步接起来计时，测“打分 → 选位 → 取 K/V”的合计时间，但到这里仍没有计算注意力输出。它同时记录了 MPS 的操作支持情况和大数组读写速度；本课主要分析上述三项与读取有关的测量。

第二组：把选择和注意力连起来，与完整读取比较（G1a）¶

现在为一个新查询准备好主注意力的 Q、历史 K/V，以及索引器所需的输入和参数，然后从同一份主 Q/K/V 出发走两条路径：

  • A：完整读取。 当前 Q 对全部合法 K 打分，做 softmax，再加权全部对应的 V，得到这个查询的注意力输出。
  • D：先选择再读取。 先为最新位置计算并写入索引向量，再计算当前查询的索引向量；用它给候选位置打分、选出名单、取出对应的原 K/V，最后由原来的主注意力 Q 对这些 K/V 重新打分、做 softmax、加权 V。索引分数负责选位置，主注意力负责计算读出。

仍以 32,768 个合法位置、额外选择 1,024 个位置为例：A 使用全部 32,768 个位置；D 每组保留开头 4 个和最近 64 个位置，再从其余位置选 1,024 个，最后对 1,092 个位置做主注意力。因此，这里的 1,092 与前面 G0 单纯取行测试中的 1,024 不同。D 必须把选择和取行的时间也付完，才能与 A 比总耗时。

两条路径都返回当前查询的注意力向量。计时从已准备好的输入开始，到 V 加权结束；不含主体的 Q/K/V 投影、注意力输出投影、MLP，也不生成答案。所以“单层注意力对照”具体指的是一层里这段读取计算的对照，并没有运行一个只有一层的语言模型。

G1a 的主 Q/K/V、索引查询输入和已有历史索引表都由程序直接随机生成，索引参数也没有训练；没有通过真实模型建立这些数组，也没有执行 RoPE。它测量这条计算路径的执行成本，不能据此判断模型选中了有用信息或还能答对问题。第四课以后才用 D0/D 区分训练前后的索引器。

实际计时时，程序预先准备了 36 套独立数组，依次对每套执行同一段计算；前一套的输出不会传给后一套。这样可以观察轮流访问不同内存区域时的耗时，不能把它理解成一次 36 层模型前向。后文会展开每轮怎样计时，以及与反复访问同一套数组的结果怎样比较。

两组实验接起来回答：先找出哪一步、哪种写法花时间，再检查把它们连成包含主注意力的流程后，是否仍有收益。单独取 K/V 快了，不等于整段注意力就快了。

下面依次看三个问题：

  1. 同一份位置名单，为什么两种 K/V 取行写法相差 25 倍？
  2. 主注意力只取约 3.3% 的历史位置，为什么总耗时不一定下降？
  3. 为什么分段时间之和不能替代整条读取路径的时间？

真实测速条件是 Mac M4 Max / PyTorch MPS。默认执行只读保存结果、展示源码、运行 CPU 小例子，不重新测速或训练。

1. 问题一：按同一份位置名单取出历史 K/V，为什么两种写法相差 25 倍？¶

本节输入是人工构造的数组。 G0 取行探针把 K 用 0.01、V 用 0.02 填充并保存为 bf16；这项实验没有输入真实文本，也没有调用 Qwen 生成缓存。

具体取的是什么？ 以 32K 档为例，一套 K、一套 V 的形状各是 [8, 32768, 128]：8 个 KV 组，每组有 32768 个历史位置，每个位置保存一个 128 维向量。本节给每组一份含 1024 个位置的名单 I[g]，取出这些位置的完整 K 行和 V 行：

K_sub[g, t, :] = K[g, I[g, t], :]
V_sub[g, t, :] = V[g, I[g, t], :]
# K_sub、V_sub 各为 [8, 1024, 128]

因此这里的“子集”是按历史位置选出的 K/V 行。两种写法使用同一份输入、同一份名单，输出形状和值相同；比较的是怎样把这些行取出来。

名单已经在计时前算好。 基准用随机生成的索引特征给出 I，各组名单可不同；三种取行实现、36 套 K/V 都复用这份 I。这一项耗时只包含取 K 和取 V，不含索引打分、top-k 或主注意力。本节名额为 k=N/32=1024，还没有加入第 2 节的首部/近期固定位置。

为何做这组对照？ G0 起初只测“按名单取 K/V 行”的成本，结果慢于预想，才追加不同写法。运行前预测及事后对照保存在项目称作“预测卡片”的文件中；25 倍差距是原预测未列出的发现。

下面是 G1a 采用的取行函数。它把 [B,G,C,d] 看成 [B*G*C,d]，把 (b,g,j) 换成 (b*G+g)*C+j 行号后使用 index_select；本例 B=1 时简化为 g*C+j。这里 B 是 batch，G 是 KV 组数，C 是每组缓存容量，d 是头维度，S 是入选数；它们是数组轴，不是后续课程的方法代号。

def flatten_cache(x: torch.Tensor) -> torch.Tensor:
    """[B,G,C,d] contiguous -> [B*G*C, d] view. No copy; raises instead of copying silently."""
    if x.dim() != 4:
        raise ValueError(f"cache must be [B,G,C,d], got {tuple(x.shape)}")
    if not x.is_contiguous():
        raise ValueError("cache must be contiguous so the flattened view is free")
    B, G, C, d = x.shape
    return x.view(B * G * C, d)

def row_offsets(batch: int, groups: int, capacity: int, device) -> torch.Tensor:
    """[B,G,1] int64 offsets that turn a position into a row id of the flattened cache."""
    return (torch.arange(batch * groups, device=device, dtype=torch.long) * capacity).view(batch, groups, 1)

def gather_rows(x: torch.Tensor, selected: torch.Tensor, offsets=None) -> torch.Tensor:
    """x [B,G,C,d], selected [B,G,S] original positions -> [B,G,S,d]; row s of group (b,g) is x[b,g,selected[b,g,s]]."""
    B, G, C, d = x.shape
    if selected.shape[:2] != (B, G) or selected.dim() != 3:
        raise ValueError(f"selected must be [B,G,S] matching the cache, got {tuple(selected.shape)}")
    S = selected.shape[-1]
    off = row_offsets(B, G, C, x.device) if offsets is None else offsets
    rows = (selected + off).reshape(-1)
    return flatten_cache(x).index_select(0, rows).view(B, G, S, d)

CPU 缩小例子。 下面用 [1,2,16,4] 的 K 和每组 8 个位置的名单，对照三种实现：拉平后的 index_select、torch.gather、高级索引。实际测速对 K、V 各做一次同样的取行；本格只需用 K 核对位置映射和输出一致性。

import torch
torch.manual_seed(0)
B, G, C, d = 1, 2, 16, 4
k = torch.randn(B, G, C, d)
selected = torch.tensor([[[0, 1, 2, 3, 9, 13, 14, 15], [0, 1, 2, 3, 5, 11, 14, 15]]])   # [B,G,S]：本例直接给定的原始位置名单
S = selected.shape[-1]

a = sparse.gather_rows(k, selected)                                      # (a) 拉平 + index_select：G1a 的写法
expanded = selected[..., None].expand(B, G, S, d)                        # (b) torch.gather 需要和输出同形状的下标
b = torch.gather(k, 2, expanded)
gi = torch.arange(G).view(1, G, 1).expand(B, G, S)                       # (c) 高级索引
c = k[torch.arange(B).view(B, 1, 1), gi, selected]

print("三种写法结果相同:", torch.equal(a, b) and torch.equal(a, c))
print("输出形状:", tuple(a.shape), "= [B, G, S, d]")
print("(a) 行号张量:", tuple((selected + sparse.row_offsets(B, G, C, k.device)).reshape(-1).shape), "个 int64 →", S * G * 8, "字节")
print("(b) 展开下标:", tuple(expanded.shape), "个 int64 → 若物化为连续张量", S * G * d * 8, "字节（是 (a) 的 d 倍）")
print("取出的 K 字节:", a.numel() * a.element_size())

这里的“36 层轮换”究竟怎样计时？ 基准预先独立分配 36 套同形状的 K/V 数组，记为 K[0],V[0] 到 K[35],V[35]。这 36 次取行之间没有 Transformer 层间依赖，前一次输出不会送给下一次；“层”只是基准把一套数组记作一层的简称。

# I 在计时前给定，各方法使用同一份名单
for layer in range(36):
    take_rows(K[layer], I)
    take_rows(V[layer], I)
# 测完整循环：预热 2 轮，计量 8 轮，每轮前后同步
per_layer_us = median(pass_seconds) / 36 * 1e6

对 32K / bf16，每套 K+V 占 128 MiB，36 套合计 4.5 GiB；一次只取其中 4 MiB 的 K/V 行。一轮依次访问第 0、1、…、35 套，下一轮才再次访问第 0 套。这样拉开了同一内存地址被再次访问的间隔。后续 G1a 的 hot 对照使用 0→0→…→0 共 36 次，而 rotating 使用 0→1→…→35；本节 G0 的取行表只有后一种访问方式。

这里要区分保存模型历史的 K/V 数组和 GPU 硬件缓存：改变数组访问顺序，是为了检查反复读取同一地址带来的硬件缓存复用。没有测硬件缓存命中率，因此“轮换”不保证每次都从主存读取。rotating 就是上面这个访问顺序，不是模型在生成 36 个 token。

三种实现的输入、名单和输出相同；32K 档 torch.gather 为 673 µs，拉平 index_select 为 27 µs，约相差 25 倍。

实现差别就在上面的代码：gather 接收 [G,k,d] 的展开下标，index_select 接收 G*k 个完整行号。expand 本身不分配那份完整下标数组；现有记录也没有证明后端是否将其物化、贡献多少耗时，不能把这一猜测当成 25 倍差距的已定位原因。

后续单层实验因此使用实测较快的 index_select 路径。这个选择由当前 PyTorch/MPS 的测量支持，不把它升级为其他后端或所有 gather 实现的结论。

2. 问题二：只取约 3.3% 的历史位置，为什么总耗时不一定下降？¶

这一节要测的是：先为当前查询挑出一些历史位置，再用这些位置原有的 K/V 做主注意力，整套操作要花多少时间。 上一节只测名单给定之后的取行，这里把产生名单和做主注意力的工作也加进来。

以本课 32K 档为例，只看某一层、某一个 KV 组：现在有 32,768 个可读取的位置，每个位置存着一个 128 维 K 和一个 128 维 V。同组查询头共用一份选位名单。完整注意力 A 读取全部位置；索引读取 D 按下面的过程选位。

先直接保留开头 4 个位置和最近 64 个位置。 这 68 个位置无论索引分数怎样，都进入主注意力，代码把它们记作 F。给开头和近期上下文预留位置，是本实验人为设定的规则；4 和 64 不是训练学出来的，也没有被本次实验证明为最优。短历史中只保留实际存在的位置，重叠的位置只算一次。

剩下 32,700 个位置，再从中选 1,024 个。这 1,024 个名额按请求开始时的长度计算：32768 ÷ 32 = 1024。配置中的 ρ=1/32 就在这里使用。68 个必留位置另外加上，因此最后读取 68＋1,024＝1,092 个位置，约占全部位置的 3.33%。这也区别于上一节只取 1,024 行的取行测量。

剩余位置中，凭什么选这 1,024 个？ 索引器先用较低维的向量给它们打分：把本组当前查询的表示投影成一个 32 维向量 u，把每个历史 K 投影成一个 32 维向量 z，再用 u 与各个候选位置的 z 做点积，选出分数最高的 1,024 个位置。r=32 指这次用于选位的向量宽度。索引器仍然需要给全部 32,700 个候选位置打分。第一课的索引参数还没有训练，“分数最高”不能直接理解为“对回答最重要”。

选完以后，取出这 1,092 个位置原有的、128 维的 K 和 V，交给主注意力。 主注意力用原来的 Q/K 重新计算权重，再组合 V。索引器只决定哪些位置可以参加，它的分数不直接充当组合 V 的权重。

本层、本 KV 组的 32,768 个位置
│
├─ 开头 4 个＋最近 64 个 → 直接保留 68 个
│
└─ 其余 32,700 个 → 用 32 维索引向量打分 → 选出 1,024 个

合并两部分，共 1,092 个位置
       ↓
取这些位置原有的 128 维 K/V
       ↓
用原 Q/K 做主注意力，得到加权后的 V

“固定”是保留规则固定，不是整个回答过程中永远读取同一批位置。 一次请求指处理这个问题及随后生成回答。每处理一个新 token，“最近 64 个位置”向前移动；当前查询也变了，因此另外选出的 1,024 个位置会重新计算。保持不变的是这次请求分配的 1,024 个额外名额，历史变长后不会不断增加。这一课只测单步成本；第二课才检查连续推进的真实模型。

历史位置的 z 可以预先算好并保存，zT 就是把它们按便于矩阵乘法的布局放在一起。参数不变时，每一步只需为新位置补上新的 z，并为当前查询计算新的 u，不用把所有旧位置重新投影一遍。

计时表中的 D_full 包含整套读取操作：为新位置补索引、计算当前查询索引、给候选打分、选位、合并位置、取 K/V、执行主注意力。full 指这些步骤全部计入，不是读取全部历史，也不是计入整个 Transformer 层。D_read 只省去“为新位置补上 z”这一步，其余查询投影、候选打分、选位、取 K/V 和主注意力仍照常执行。它假定索引表已经建好，不是假定位置名单已经给定；名单给定的纯取行测量是上一节的另一项实验。

运行前预测。 G0 用 A 的理想读取时间减去当时实测的索引链成本，得到 8K 持平偏负、16K 持平偏正、32K 正收益；同时预测 D 有一部分不随历史长度显著改变的固定成本。下面把 D 的全部步骤算进去检查。

def sparse_decode_step_kernel(q_main, q_pre, k_cache, v_cache, zT, wq_t_scaled, wk, fixed_rows, off_lo, lo: int,
                              hi: int, k: int, selected_count: int, *, k_pre_new=None, write_col: int = -1,
                              scale=None, backend="sdpa"):
    """One layer's D read for one new query (T == 1). Every D-only cost is inside this function."""
    B, G, h, T, d = q_main.shape
    if T != 1:
        raise ValueError("a decode step takes exactly one new query position")
    if k_pre_new is not None:
        zT[..., write_col:write_col + 1].copy_(project_keys(k_pre_new, wk))   # z of the newest key, its own column
    u = project_queries(q_pre, wq_t_scaled)                                     # [B,G,1,r]
    rows = select_rows_kernel(u, zT, fixed_rows, off_lo, lo, hi, k)
    k_sub = flatten_cache(k_cache).index_select(0, rows).view(B, G, selected_count, d)
    v_sub = flatten_cache(v_cache).index_select(0, rows).view(B, G, selected_count, d)
    return subset_attention(q_main, k_sub, v_sub, scale=scale, backend=backend)
def select_rows_kernel(u, zT, fixed_rows, off_lo, lo: int, hi: int, k: int) -> torch.Tensor:
    """Score the candidate columns once, top-k once, merge with the fixed rows. Returns flat row ids [B*G*S]."""
    B, G = fixed_rows.shape[:2]
    if k <= 0:
        return fixed_rows.reshape(-1)
    scores = candidate_scores(u, zT, lo, hi)                       # [B,G,1,M]
    top = torch.topk(scores, k, dim=-1).indices.view(B, G, k)      # the only top-k, over the candidate domain
    return torch.cat([fixed_rows, top + off_lo], dim=-1).view(-1)

把上述操作对应到函数。 本档有 H=32 个查询头、G=8 个 KV 组，每组 h=4 个查询头，头维度 d=128；索引器先把同组四个查询拼成 512 维，再投影到 r=32。各组分别打分、选位，不共用一份分数名单。这里的 H=32 是本课合成数据的形状；第二课 Qwen3-0.6B 的 H=16。

这组函数为真实模型约定：q_pre/k_pre 接收归一化后、RoPE 前的 Q/K，q_main/k_cache 接收主注意力所用的 Q/K。但本课的测速没有执行真实模型或 RoPE：主 Q/K/V、已有索引表 zT 和 q_pre 都是直接随机生成的数组。 每次测 D_full 时，实际执行的是给新键投影并写入最后一列 z、计算当前 u、打分选位和主读取；没有在本次计时里从全部历史 K 重新建立索引表。第二课才从真实模型中按这个接口提取特征。取行函数始终使用原位置对应的 K，不重新编号或额外旋转。zT 按 [B,G,r,C] 保存。查询形状 [B,G,h,T,d] 中 T 是本次输入位置数，此处 T=1；backend="sdpa" 指下方主注意力调用 SDPA 接口。

3. 问题三：各段单独计时相加，为什么不等于完整执行¶

这两种计时没有执行同一段程序。 分段实验先准备好一份分数，再反复测“从这份分数选位置”；测取行时，又直接使用一份预先准备好的名单。整段实验则要求本次算出的分数真正产生名单，再用这份新名单取 K/V：

分段测量：预备分数 → 测选位；预备名单 → 测取行；预备 K/V 子数组 → 测注意力
整段测量：本次查询 → 本次分数 → 本次名单 → 本次 K/V 子数组 → 本次注意力输出

因此，前一种测法的后半段可以反复使用同一批中间数据；后一种必须在本次执行中依次产生它们。下面源码里的 s0、top0、rows0、ksub0/vsub0，分别就是预备分数、候选名单、合并后的行号、入选 K/V。

运行前的预测。 G1a 卡片预测“分段之和高于链式 20% 到 30%”，理由是分段计时里每个算子独立提交，链式执行可以让提交与执行重叠。实测方向相反：整段执行比各段单独计时之和更慢，8K 多 6%，32K、ρ=1/8 多 28%。下面保留原测量，随后说明它能支持什么解释。

公式更正说明的是什么。 比较两条路径时，两边必须用同一套成本划分。S1 已经把索引读与入选 KV 读按理想载荷扣掉，再减去包含同一批工作的实测链式，就扣了两次。更正后 D 更有利，三个长度的方向不变；但 G1a 实测 8K 与 16K 比两版预测都更不利。上一格末尾给出了原因：不是 A 比带宽情景更快（A 实测 110 µs，比 86 µs 的情景值慢），而是 G0 的链式成本范围不完整，漏掉了索引查询投影、索引键追加、合并与子集注意力。这张 G0 表因此仍不是完整解码步的净收益预测。

5. 边界与下一步¶

  • 平台。 性能测量来自一台 M4 Max 的 MPS 后端与 torch 2.14.1。原语成本、SDPA 内核选择、compile 行为在 CUDA 上可能不同。
  • 范围。 单层、随机张量、batch 1、一步解码。整模型每步时间、连续生成、k 固定下合法长度增长、真实 Q/K 分布都留给 G1b。
  • 索引器。 随机初始化，没有训练。它回答的是"筛选路径的计算成本有没有空间"，不是"模型能只看 3% 的历史而保持能力"。任务质量对照（G2，第三课展示其缩减版）才检查答题。
  • 门槛。 bf16、32K、ρ=1/32 的 D_full/A = 0.74（6/6 进程 ≤ 0.90）满足了 10% 的继续研究门槛。10% 是继续投入的门槛，不是架构定理。
  • 补测。 PR #1 评审后的交错顺序、容量四格、折叠手写 A 对照见 reports/g1a_supplement_mac_m4max.md。
