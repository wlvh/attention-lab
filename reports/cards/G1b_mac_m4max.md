## 问题与执行前预测

**三个问题。** (1) 接入后有没有把原模型算错：未改模型、封装完整路径、封装加静态缓存三者在 32 / 128 / 512 位置上的词表分数与缓存状态是否落在预设容差内。(2) 单层省下的时间放进完整模型还剩多少：bf16、batch 1、N0 ∈ {8192, 16384, 32256}、ρ = 1/32、r = 32 时，一步完整前向（模型入口到下一 token 的词表分数）D 对 A 的比值是多少。(3) 连续推进时缓存、索引表和执行效率是否稳定：固定 k0 下合法长度每步加一，128 步内每步耗时、内存、重编译有没有失控。

**模型与设置。** Qwen/Qwen3-0.6B，Hub revision `c1899de289a04d12100db370d81485cdf75e47ca`（config.json：28 层，16 查询头，8 KV 头，head_dim 128，hidden 1024，词表 151936，tie_word_embeddings）。主体冻结，索引器为未训练的随机分组索引器（P0，不加索引 RoPE），每层一对 (Wq, Wk)，r = 32。四条路径同一模型对象、同一 token、同一设备，各自维护缓存：`native_dynamic`（未改模型 + transformers DynamicCache，库默认，每步 torch.cat）、`native_static`（未改模型 + StaticCache，容量 N0+128）、`wrapped_full`（封装 + 静态 LabCache，读全部合法位置，即 A）、`sparse`（封装 + LabCache + 索引表，G1a 的索引读取并含全部 D 新增成本，即 D）。容量 C = N0 + 128；Prefill 按 2048 一块；固定 N 单步按回文顺序循环（预热 10、循环 50），连续 128 步各 3 次，每步前后 `torch.mps.synchronize()`；`logits_to_keep=1`（所锁 transformers 5.20.0 的接口名已核对）。剖析与编译另跑。不设 `PYTORCH_ENABLE_MPS_FALLBACK`，不关内存保护。

**容差（预设，写在 `configs/mac_gate1b.json`，不为通过而放宽）。** float32：词表分数 max|Δ| ≤ 1e-2、相对范数 ≤ 1e-3、argmax 一致 ≥ 99%，缓存 K/V 每层 max|Δ| ≤ 1e-3；bfloat16：max|Δ| ≤ 1.0、相对范数 ≤ 2e-2、argmax 一致 ≥ 95%，缓存 ≤ 0.25；tiny 随机模型 float64：1e-9 / 1e-10。全选位置的 D（k0 = 容量）必须在同一容差内对应封装完整路径；只读部分历史（ρ = 1/8）只记录不要求相等。只看生成文本相似不算通过。

**预测的依据。** (a) G1a 正式六进程（bf16、eager、轮换）每层读取阶段：8K A 110 / D_full 195 µs，16K 203 / 222，32K 405 / 297；补测交错配对 32K 为 0.67。乘 28 层只是量级：8K A 3.1 ms 对 D 5.5 ms（D 多 2.4 ms），16K 5.7 对 6.2（多 0.5），32K 11.3 对 8.3（**少 3.0 ms**）。(b) 权重读取：0.6B 的层内权重约 0.88 GB（bf16），lm_head（与嵌入共享）0.31 GB，每步至少读 1.19 GB；按 G1a 的 A 有效带宽 330 GB/s 与 G0 扫描 390 GB/s，仅权重就要 3.1 到 3.6 ms，M=1 的矩阵向量乘通常达不到满带宽，取 4 到 7 ms。(c) 提交开销：G0 测得小算子在流提交成本约 24 µs/个，G1a 的 D 八算子链每层 180 到 300 µs 与之一致。按已安装的 `modeling_qwen3.py` 数：每层 RMSNorm 三次各 8 个算子、q/k/v/o 四个线性层、RoPE 约 10 个、缓存写入 2 到 4 个、SDPA 1 个（MPS math 路径内部还会拆成多个内核）、MLP 5 个、残差 2 个，约 55 到 60 个 aten 算子，28 层约 1650 个，再加嵌入、末层 norm、lm_head。若 CPU 提交不能与 GPU 执行重叠，仅提交就是 33 到 42 ms；HF 前向的 Python 开销同量级并与之部分重叠。D 每层比 A 多约 10 个算子（z 追加、u 投影、候选打分、top-k、合并、两次 index_select、子集 SDPA 替代一次 SDPA），28 层多约 280 个，按 24 µs 计多 6 到 7 ms 的 CPU 时间。

**主预测（整步 D/A，bf16，eager）。** 0.6B 模型在 MPS 上的一步前向以 CPU 侧提交和 Python 开销为主，GPU 侧（权重 4 到 7 ms + 注意力 3 到 11 ms + 其余）小于 CPU 侧，于是 **G1a 在 32K 省下的约 3 ms 注意力读取被提交开销的底掩盖，而 D 多出的约 280 个算子直接加在 CPU 关键路径上**：

| N0 | A（wrapped_full）整步预测 | D（sparse）整步预测 | 整步 D/A 预测 | 方向 |
|---:|---:|---:|---:|---|
| 8192 | 35–55 ms | A + 5 到 9 ms | 1.10–1.25 | D 更慢，不通过 |
| 16384 | 35–55 ms（与 8K 相差 ≤ 3 ms） | A + 4 到 8 ms | 1.08–1.20 | D 更慢，不通过 |
| 32256 | 36–58 ms | A + 1 到 7 ms | **0.98–1.15** | 持平偏慢，不通过 |

写明：**G1a 的 0.74（六进程）与补测的 0.67（配对）是单层读取阶段的测量，与这里的整步比值是不同范围的量，不要求复现**；即使 32K 的 3.0 ms 节省全部显露，占 36 到 58 ms 的整步也只有 5% 到 8%，低于 10% 门槛。因此主预测是：eager 下三个 N0 都不通过性能门槛，且比值对 N0 的依赖很弱。把握：七成。替代结果（三成）：若 MPS 运行时把提交与执行重叠得好、整步实际由 GPU 决定（A ≈ 18 到 25 ms），则 32K 的 D/A 可到 0.85 到 0.95，8K 仍 > 1.2。

**其他预测。**

- **原生对照。** `native_static`/`wrapped_full` 在 0.90 到 1.20：HF 的 SDPA 在 MPS 上走 `enable_gqa=True`（`integrations/sdpa_attention.py` 的 `use_gqa_in_sdpa`），G1a 在 32K 测得它比 fold 慢 65%（每层 +0.26 ms，28 层 +7 ms），再加每步在设备上构造 [1,1,1,C] 遮罩的几个小算子；若整步被 CPU 决定，这些 GPU 侧差别大部分被掩盖，比值接近 1.0 到 1.1。`native_dynamic`/`wrapped_full` 在 0.90 到 1.35：每步 torch.cat 复制整段 K/V（32K 每层 134 MB，28 层 3.7 GB，GPU 侧约 10 到 12 ms），被 CPU 底掩盖多少取决于重叠程度；8K 时 cat 只有 0.9 GB，接近 1.0。封装没有把原模型算慢：`wrapped_full` ≤ `native_static` × 1.05。
- **连续 128 步。** 封装两条路径每步耗时在 128 步内平坦（首 16 步与末 16 步中位数相差 ≤ 5%，最小二乘斜率 |slope| ≤ 20 µs/步），k 恒等于 k0（8192 → 256，16384 → 512，32256 → 1008；按 round(ρ·(N0+1)) 计），selected_count = 68 + k0 恒定，合法长度每步加一；`torch.mps.current_allocated_memory` 对封装路径恒定，对 `native_dynamic` 随步小幅上升并伴随分配器抖动；eager 下没有重编译（没有编译对象）。
- **Prefill。** 2048 一块：8K 约 1.5 到 4 s，16K 5 到 10 s，32K 15 到 35 s（注意力部分按 ½·N²·H·d·4 flop 计 32K 约 123 TFLOP，MPS bf16 有效 8 到 15 TFLOPS）；D 的 Prefill 比 A 多 ≤ 3%（z 构建是 r = 32 的小矩阵乘）。四条路径的 Prefill 相差 ≤ 25%。
- **数值。** float32 的三段对照全部落在容差内，且观测到的差别比容差小一个量级以上（max|Δ| 约 1e-4 到 1e-3）；bf16 的 max|Δ| 在 0.1 到 0.5，argmax 一致 ≥ 97%；全选 D 对封装 A 的差别与前者同量级；回退后重算逐位相同（同形状、同内核）；分块与一次构建的 K/V/z 在 float32 下 ≤ 1e-3。未改模型 MPS float32 对 CPU float32 的差别（平台噪声底）与封装对未改模型的差别同量级。
- **剖析。** D 的一步里没有任何内维 128 且触及 N0+1 或容量 C 的 matmul 类算子；A 的一步里 SDPA 以 `_scaled_dot_product_attention_math_for_mps` 出现并触及合法长度；D 的 aten 算子数比 A 多 250 到 320。
- **编译（一轮有依据的修正，若 eager 不通过）。** 把 MLP 与三处 RMSNorm 换成同数学顺序的共享 `torch.compile` 函数，四条路径同时受益：五成把握 MPS 的 inductor 能编译；若能，整步 CPU 侧减少约 800 个算子，A 降到 20 到 35 ms，32K 的 D/A 落到 0.85 到 1.00（当 CPU 底低于 GPU 时间时显露 G1a 的节省），8K 仍 > 1.1。编译期间无重编译（T=1 形状固定，`error_on_recompile=True` 守卫）。
- **内存。** 四套缓存在 32384 容量约 15 GB，加权重 1.5 GB 与 Prefill 临时量约 4.5 GB，峰值 < 25 GB，不触及 80 GB 预警。
- **若不通过的处理（预先登记）。** eager 不通过且剖析确认提交开销主导 → 只做上述编译这一轮修正并两边同测；修正后 32K 仍无每个循环都 ≤ 0.90 的证据 → 状态 `correct_but_not_faster`，收口速度主线，不训练、不换更大模型；数值或缓存不对应 → 停在接入排错，不测速。

连续 128 步的每步中位数与单步一致（封装 A 13.39 / 15.85 / 20.83，D 16.86 / 17.89 / 19.05）。原生 StaticCache 比封装 A 慢 5% 到 8%；原生 DynamicCache（库默认，每步 torch.cat 整段 K/V）在序列里是 16.7 / 23.9 / 39.3 ms，比封装 A 慢 25% / 51% / 89%，单步"恢复后再走一步"的口径下更慢（24 / 37 / 75 ms）。Prefill（ms）：8K 1671 / 1832 / 1779 / 1745，16K 4672 / 6274 / 5113 / 5172，32K 19850 / 32719 / 21421 / 21096（顺序：原生动态 / 原生静态 / 封装 A / D）；D 的 Prefill 含索引表构建，与封装 A 相差 −1.5% 到 +1.2%，在噪声内。

**问题三：连续推进是否稳定。** 稳定。128 步序列（3 次）里每步时间的最小二乘斜率在 −31 到 +1.7 µs/步之间（负值来自序列开头几步稍慢的瞬态），封装 A 首 16 步与末 16 步中位数相差 ≤ 0.7%，D ≤ 2.8%（19.84 → 19.30），原生静态最大 9%（24.00 → 21.83，开头瞬态）；k 在请求内恒等于 k0（256 / 512 / 1008），读取数恒为 68 + k0，合法长度每步加一；`torch.mps.current_allocated_memory` 在 128 步内对四条路径都恒定（32K 时 16.717 GB，分辨率 1 MB；DynamicCache 每步理论增长 115 KB，128 步 14.7 MB，低于分辨率）；eager 无编译对象，块编译期间 dynamo 新图数为 0、无重编译错误。32K 时四套缓存加权重的分配峰值 16.72 GB（driver 24.9 GB），进程 RSS 1.13 GB，无 80 GB 预警。

**剖析（与计时分开）。** 32K 一步：非视图 aten 算子数 封装 A 3041、原生静态 3421、D 3463（比 A 多 422）；CPU 侧自时间 4.0 / 5.1 / 8.4 ms，对比整步墙钟 21.2 / 22.7 / 19.7 ms，**三条路径都不是 CPU 提交受限**。D 的一步里没有任何触及合法长度或容量且内维 128 的 matmul 类算子（28 次 top-k、56 次 index_select 加 1 次嵌入查表、84 次 bmm）；A 的 SDPA 走 `_scaled_dot_product_attention_math_for_mps`；原生静态的 SDPA 带遮罩读满容量 32384。D 多出的 84 个 bmm（z 投影、u 投影、候选打分，每层 3 个）每个 CPU 自时间约 35 µs。

## 支持的解释与替代解释

**支持的解释。** 把一步拆成"与 N 无关的基底 + 注意力读取"：封装 A 在 8K / 16K / 32K 是 13.3 / 16.0 / 21.2 ms，按 G1a 的每层 A 时间乘 28 层（3.1 / 5.7 / 9.9–11.3 ms）扣除，基底约 10.2 ms，三个 N0 一致。基底里权重读取 1.19 GB 按 G1a 的 330 GB/s 只占 3.6 ms，其余是约 3000 个非视图小算子在 GPU 时间线上的固定开销（每个 2 到 3 µs 量级）；CPU 侧只用 4 ms，所以**瓶颈在 GPU 时间线的核数量，不在 CPU 提交**——这推翻了预测段的机制，但保留了结论的形状：固定底决定一切。D 的链在模型里每层 211 µs（8K）到 340 µs（32K），由 14 个相互依赖的小核组成，G1a 测到的"链式高于分段之和"在这里也成立；它多出的 422 个算子在 8K 处值 2.8 ms（每个约 6.7 µs），注意力字节的节省要到 32K 才能盖过它。**单层省下的时间放进整模型剩一半：** 同形状探针里 D 比 A 每层省 110 µs（352 对 240 µs），28 层 3.1 ms；整步实测只省 1.5 ms（21.21 − 19.68），再除以 21 ms 的整步就是 7%。这正是"单层快不等于整模型快"的两个原因：一个是注意力之外还有 10 ms 的基底摊薄比值，一个是 D 的小核链放进更长的依赖链后每层贵了约 100 µs。

原生 DynamicCache 的慢（32K 序列 39 ms）来自每步 torch.cat 复制 3.7 GB 的 K/V，在 GPU 时间线上约 11 ms，加上单步口径下 crop 后再 cat 的额外复制；它是 transformers 的默认路径，不是人为慢基线，但也不是本项目的 A（本项目的 A 是封装 A 与原生静态）。原生 StaticCache 慢于封装 A 的 5% 到 8% 与两件事一致：`enable_gqa=True` 的 SDPA（G1a 测得 32K 慢 65%，这里被基底摊薄）和每步在设备上构造 [1,1,1,C] 遮罩并读满容量。

块编译没有改变格局（A −2% 到 −5%），因为融合的是 RMSNorm 与 MLP 的逐元素链，而基底里的核多数是矩阵乘和注意力核，与 G1a"编译只影响几个几 µs 的视图与加法"一致。

**替代解释，未排除。** (1) 运行状态：32K 配对比值 0.872 到 0.986，50 个循环里 7 个 ≤ 0.90，回文顺序与交替序列已经消除固定顺序效应，但温度与分配器状态仍可能解释 ±5% 的摆动，正式只跑了一个进程（G1a 跑了六个）。(2) "基底 10 ms 由核数量决定"是由 A 的三点与 D 的差值推出的，没有 GPU 时间线剖析（MPS 的 torch.profiler 只给 CPU 时间）；用 Instruments / signpost 看时间线会改变性能，必须单独做。(3) D 在模型里每层 340 µs 对探针 240 µs 的差额可能来自依赖串行化、分配器或 bf16 内核选择，未分离。(4) 单步口径（每次恢复状态再走一步）与序列口径对 DynamicCache 给出 74 对 39 ms 的差别，说明"恢复"方式影响该路径；封装路径两种口径一致（21.2 对 20.8）。

**不能推出什么。** 没有任务与质量结论；只测了 Qwen3-0.6B、bf16、batch 1、ρ = 1/32、未训练的随机索引器、MPS。更大的模型基底更大（权重字节线性增长），同样 N 下比值更接近 1，除非 N 更长；本机原生上下文按 32,768 控制，更长要另验。CUDA 的核启动成本与融合注意力核不同，不能由此推 4080 的结论。编译只试了块级融合；全图编译与自定义 Metal 核未试。

## 决策与边界

**工程完成：是。** 数值对应（float32 预设全过且余量一个量级；封装逐 token 路径与库自身逐 token 路径逐位相同；bf16 修订判据全过，预设未过的 17 项已逐一归因于库自身舍入）、缓存与索引连接正确（契约测试、未写槽与未来位置不可见、回退后旧后缀不可读、分块与一次构建一致、z 取自 RoPE 前、每步各写一次、无跨分支别名、无 torch.gather、每层一次 top-k）、连续 128 步与回退通过、结果可由 `scripts/g1b_report.py` 从记录重生成。

**性能通过：否——`correct_but_not_faster`。** 同模型、同设备、同工作量下，没有设置呈现每个循环都 ≤ 0.90 的整步收益：32K ρ = 1/32 的 D/A 配对中位 0.930（0.872–0.986，7/50 个循环 ≤ 0.90），16K 1.054，8K 1.210；块编译同测后 0.934 / 1.103 / 1.225。32K 是"有收益但不足 10%"的临界档，与 G1a 的 32K ρ = 1/8 档类似。

**预登记的修正轮。** 预测段登记的修正（块编译，两边同测）已做，未改变格局；剖析把主要抵消项定位到 D 链的核数量而非 CPU 提交，于是用同形状探针检验了"少两个核"的 D 变体（行号原位装配 + K/V 堆叠后一次 index_select，输出与 G1a 核逐位相同）：每层省 7 到 15 µs，整步省 0.2 到 0.4 ms，32K 的 D/A 从 0.930 变到约 0.915，到不了 0.90。因此没有为它跑正式一轮、没有改缓存布局：这就是"修一轮仍无可行证据"的保存案例。要越过门槛需要把 D 的 14 个小核融合成少数核（自定义 Metal 核或可用的融合算子），这超出本关范围与现有授权的工程量。

**按预登记规则：收口速度主线。** 不以速度为前提进入 G2，不训练索引器，不换更大模型（更大模型只会放大基底）。可行组合表：

| dtype | N0 | ρ | 整步 D/A（eager / 块编译） | 结论 |
|---|---:|---:|---|---|
| bf16 | 8192 | 1/32 | 1.210 / 1.225 | 不通过，D 更慢 |
| bf16 | 16384 | 1/32 | 1.054 / 1.103 | 不通过，持平偏慢 |
| bf16 | 32256 | 1/32 | **0.930 / 0.934**（0.87–0.99） | 不通过，收益 7%，临界 |

边界：10% 是投资门槛不是定理；7% 的收益是真实、可重复（100 次单步、3 × 128 步、两种模式一致）但不足以支撑后续训练投入；对更长上下文、CUDA 轨道、融合核三条路径本关没有证据，也没有授权启动。
