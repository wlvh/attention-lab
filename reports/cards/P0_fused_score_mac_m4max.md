## 问题与执行前预测

**问题。** 把 D 链里的 z 写入、u 投影、候选打分三段（PyTorch 路径是 3 个 bmm + 1 个 copy_，共 4 次核调用）做成一个 Metal 核，32K 处每层能否 ≤ 80 µs，数值是否与 float32 参照一致。

**设置。** 随机张量、bf16、B=1、G=8、h=2、d=128、r=32；N0 ∈ {8192, 16384, 32256}，容量 N0+128，合法长度 L = N0+1，候选域 [4, L−64)，M = L−68（8125 / 16317 / 32189）；28 层轮换工作集，预热 20、正式 50 pass，每 pass 前后 `torch.mps.synchronize()`；至少两个独立进程。对照：`pytorch_chain`（project_keys + 列写 + project_queries + candidate_scores）、`pytorch_score_only`（candidate_scores）。变体：`fused_1launch`（每个线程组自行算 u，组内第 0 个线程组写 z 列）、`fused_2launch`（序曲核 + 打分核）。

**预测的依据。** G1a 的分段计时（bf16、每层）：z 追加 27 到 28 µs，u 投影 25 µs，候选打分 36 / 45 / 61 µs（8K / 16K / 32K），链式比分段之和多 6% 到 28%。zT 候选段字节：G·r·M·2 B = 4.2 / 8.4 / 16.5 MB；G1a 的 A 有效带宽 330 GB/s，G0 扫描峰值 390 GB/s。G1b 推得模型内每个小核的固定成本 7 到 20 µs。

**预测。**

| 项 | 8K | 16K | 32K |
|---|---:|---:|---:|
| `pytorch_chain` µs/层 | 90–115 | 100–125 | 115–145 |
| `pytorch_score_only` µs/层 | 33–42 | 42–52 | 56–70 |
| `fused_1launch` µs/层 | 25–40 | 35–55 | **55–85** |
| `fused_2launch` µs/层 | 30–45 | 40–60 | 60–90 |
| fused / pytorch_chain（32K） | | | 0.45–0.65 |

- 32K 处 `fused_1launch` ≤ 80 µs 的把握六成：带宽部分 42 到 55 µs（16.5 MB 按 300 到 390 GB/s），加一次启动与尾部延迟 10 到 20 µs，加序曲（每线程组冗余算 u，权重 16 KB 命中缓存）5 到 10 µs。若 Metal 核对 bf16 列读取的合并不理想（每线程沿 r 跨列读），带宽利用可能只有 60%，那就是 70 到 95 µs，门槛失守。
- 两次启动的变体比一次启动慢 5 到 15 µs（多一次启动），但序曲不冗余；若一次启动变体的序曲开销出乎意料地大，两者可能反转。
- 数值：fused 输出 fp32，对 CPU float32 参照的相对范数 ≤ 1e-6（32 项 fp32 累加），**比现有 PyTorch 路径更准**：PyTorch 的 bmm 输出是 bf16，对同一参照的相对范数约 2e-3 到 5e-3。z 列对 `project_keys`：≥ 99% 元素逐位相同，其余差 1 个 bf16 ulp（累加顺序不同）。fused 分数与 PyTorch bf16 分数各自 top-k（k = 1008）的入选集合一致率 97% 到 99.5%（bf16 平局与边界重排）。
- 毒化候选域外的列（含 write_col 以外的近期窗口与未写槽）为 NaN，分数仍有限；M 不是 256 的整数倍时边界线程不越界。
- 若通过，推到整模型（估算，不是本关测量）：D 链每层从约 340 µs 降到约 250 到 280 µs，32K 的 D/A 从 0.930 到约 0.84 到 0.88，仍不足以单独过线——P0 只是三段里的一段，剩下的 top-k、取行、子集注意力要靠 P1/P2。

## 支持的解释与替代解释

**支持的解释。** 这一段的下界由 zT 扫描的字节决定：16.5 MB 按 274 GB/s（PyTorch 的 bmm 实测）是 60 µs。v2 核达到 236 GB/s，加上序曲（每个线程组冗余算一次 u，约 32 个线程组每组）与启动延迟，70 µs 已经接近下界；它比 PyTorch 四算子链快 32 µs（三次启动与一次跨步列写被吃掉）。**第一版慢在访存宽度而不是核数量**：每线程每次只读 2 字节，一个 simdgroup 一条指令只取 64 字节，又有 1008 个线程组各算一次 u；换成 8 字节向量读取与四分之一的线程组后带宽从 79 升到 236 GB/s。这与 G1b 卡片"核数量决定一切"的解释并不矛盾，但补了一条：**自定义核只有写对访存模式才能兑现减少启动的收益**。两次启动变体慢是因为序曲核没有优化（一个线程一个输出、跨步读 256 项），不是两次启动本身的代价；它不是门槛对象，没有继续调。

**对整模型的含义（估算，不是本关测量）。** 打分段在 G1b 推得的 D 链 340 µs/层里约占 100 µs；换成 70 µs 每层省约 30 µs，28 层约 0.9 ms，32K 的整步 D/A 从 0.930 到约 0.89：单靠这一段不足以稳定越过 0.90。范围说明里的三核设计需要 P1（取行 + 子集注意力）与 P2（选择）各自达到门槛，才有望把 D 链压到约 150 µs/层、整步比值到 0.65 到 0.75。

**替代解释，未排除。** (1) 两进程的 32K 结果几乎相同（69.7 与 70.0），正反序差 1 µs，但 8K / 16K 处 pytorch_chain 在正反序间差到 25%（75 到 105 µs），说明小算子链对运行状态敏感，fused 核的优势在短长度上的数字（0.48 到 0.63）不如 32K 稳定。(2) 236 GB/s 是"扫描字节 ÷ 核耗时"的有效值，核内还做了序曲与写出分数（1 MB），真实带宽利用略高于此。(3) 随机张量的 zT 没有缓存局部性可利用，真实索引表也没有，这里不构成偏差；但 top-k 一致率是对随机分数算的，真实分数的平局结构不同。
