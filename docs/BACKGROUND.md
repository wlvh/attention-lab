# 背景与问题演进

本文是当前对话的项目相关摘要，不是逐字对话记录。用户转贴的 Fable 5.1 评审归于其评审内容，不归为用户原创。除本项目所需硬件、工作方式与预算外，不引入用户其他项目或个人资料。

## 出发点

用户通过一系列追问整理了《QKV：Transformer 计算图谱》HTML。关注的是中间结果怎样产生、历史怎样保存复用、哪些计算可以并行、架构与执行如何改变实际收益。原则是 **What I cannot create, I do not understand**：能重建关键过程、预测改变条件的后果、检验失败边界，而非仅能复述术语。

教材中索引筛选的核心是：较便宜的索引打分决定哪些历史位置参加主注意力；真正的贡献仍由主 Q/K 重新打分并汇总 V。未选中历史仍可以保留，之后再次选择。见 `reference/handbook_with_exercises_updated(4).html#attention-index-comparison`。

## 为什么没有沿用“从零训练查表模型”方案

早期助手提出先训练随机资料查询任务，再做缓存、机制解释和架构改造。用户明确追问训练目的，并提出真正想比较不同读取方式的推理速度与任务性能。

因此主线改为：使用现成开放权重模型，冻结主体，替换读取方式；只有新增小索引器需要学习时才训练。查表材料变为可自动判分的测试工具，不再是从零训练语言模型的目的。早期训练方案存档，不是待办。

## v2 → v3 → Mac 执行补充

v2建立对照、预算和状态正确性；Fable 5.1指出应先量化性能空间、先做微基准、长上下文更重要、模型规模与速度敏感度存在冲突、RoPE后投影有位置风险。后续评审接受这些方向，并收窄“必然更慢”等过强说法。

v3形成五关：执行可行性→基线有效性→索引可学习性→联合取舍→可选分层改进。之后评审补充 A-best、RoPE前索引表构建、请求内固定k、coverage与输出误差的关系、配对统计、可行组合交集等约定。

用户最新操作决定：优先 MacBook，4080 为 Windows 主机且自述 16GB 内存；希望 Codex 全程执行，随后以 Jupyter 式分段代码进行解读。因此当前方案不是直接照搬 v3 的 CUDA 关卡，而是保留科学问题、增加 MPS 能力预检与独立设备轨道。

## 预训练模型为什么可以加模块

现成参数 θ 适用于原计算 F_A(x;θ)。加索引器参数 φ 后，计算变为 F_A'(x;θ,φ)。θ不变，不代表函数不变。我们复用原 q/k/v/o 投影、归一化、RoPE和前馈，只替换历史选择及注意力执行接口。形状兼容只证明接得起来，任务能力仍须重新验证。

密集教师阶段，主体完整读取提供detach特征和教师分配；新索引器的连续分数用KL学习。部署时才通过top-k名单控制读取。若只把top-k整数下标用于gather，答案损失不会沿这些下标自动训练索引器；这不等于top-k返回的数值在任何用法下都不可求导。

本轮不更新主体，不探索稀疏架构充分训练的能力上限。改造掉分可能来自选择失误、预算过小、原主体不适应或多层状态变化，不能直接写成某种架构优劣。

## 学习与执行如何协作

Codex承担实现、测试、重复实验、日志与首版讲解。用户掌握目标、取舍、预算和验收。先保留预测再运行，事后讲解真实结果；不是在结果出现后补一段“本来就知道会这样”的故事。

只维护一份正式Python实现，Notebook调用和展示它，HTML是已执行的阅读副本。目标是第一份真实实验课，不是先造一个复杂教学平台。
