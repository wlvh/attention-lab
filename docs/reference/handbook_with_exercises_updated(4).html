先看全景

哪些层次共同决定 KV 缓存的实际收益？

KV 缓存保存模型已经算出的中间状态，供后续计算复用。这里的实际收益，包括少占存储、少做重复计算、缩短等待和降低整个任务的费用，也可能让同样的设备支持更长输入或更多并发任务。这些收益都要以任务仍能正确完成为前提。

先分清：模型的“层”、层里的“头”和 token 的位置

先以常见的 Transformer 语言模型为例。模型由一层接一层的计算模块组成，每个模块叫一个模型层，也叫解码器层（decoder block）。第一层接收 token 转成的初始数值，后面的层接收前一层的结果。一个层的内部包含注意力计算和前馈网络等部分；多个注意力头，位于这一层的注意力部分里面。

后文还会比较两种共享：同一层内的多个头共享 K/V，这是 GQA／MQA 讨论的范围；不同模型层共享 K/V，这是 YOCO 的做法。共享历史记录后，各头、各层仍可产生自己的查询和计算结果。查看 MHA、GQA、MQA 与 YOCO 的对照表。[7][11]

01
小王 · 问

前图里，注意力之后还有一段“前馈网络”：继续加工当前 token 的内部数值。听说 MoE 会把一个 token 交给少数几个专家处理。

这些专家和注意力头是什么关系？选中两个专家，会多出两套历史 K/V 吗？

大王 · 答

先看它发生在哪里。这里介绍的是把前馈部分换成专家网络的常见 MoE 结构。注意力先读取前文信息；随后，前馈部分用训练得到的参数，继续加工当前 token 的内部数值。

混合专家（Mixture of Experts，MoE）为这一步准备多套参数不同的前馈网络，每套叫一个专家。一个负责打分和选择的小模块——路由器（router）——根据当前 token 的内部数值，挑出少数专家执行，再合并它们的输出。这样可以增加模型可用的参数总量，同时让一个 token 只执行少数专家的计算。专家与注意力头位于本层的不同部分。[62]

实际模型也把这两种数量分开设置。Qwen3-30B-A3B 有 128 个专家，每个 token 激活 8 个；注意力却是 32 个查询头、4 个 KV 头。因此它每层按 4 个 KV 头保存历史，不按 8 个或 128 个专家来算。[63]

MoE 会怎样影响缓存的实际收益？

  • 命中旧前缀，也能少做旧 token 的专家计算。后续层需要的历史 K/V 已准备好，通常不必再走一遍产生这些状态的计算；新 token 仍需完成自己的注意力和专家计算。
  • 只选少数专家，不代表只存少数专家的参数。专家参数与请求产生的 KV 是两种数据。若更多专家权重占用显存，留给 KV 的空间就可能减少。
  • 少算的收益，要扣除分发和汇合的代价。专家若分布在不同 GPU 上，还要传递当前 token 的内部数值、汇合结果。具体加速多少，取决于计算、存储和通信的共同开销。[64]

评价时要同时看：保存体积与运行峰值、重复输入的缓存命中、恢复时间、首字等待、单个回答的生成速度、多人同时使用时的处理量、总成本和任务正确性。例如，把缓存移到更便宜的存储中，可能降低费用，却增加取回时间；额外发请求保活，可能增加眼前开销，却避免下一轮更贵的重算。后文会分别说明这些收益与代价从哪里来。

01 / COMPUTATION · 从计算开始

先弄清：KV 到底是什么？

缓存的价值来自少做重复计算。理解这件事，需要先区分“读入已有输入”和“生成新的内容”。

02
小王 · 问

我评价一个新模型时，通常先看它答得准不准、生成得快不快。但如果让它连续读代码、运行测试、修复错误，同一份项目资料和越来越长的对话会被反复带回。

这些重复输入为什么值得单独关注？缓存省下的计算，会怎样影响整个任务的费用和耗时？

大王 · 答

设想一个会读代码、调用终端并修复错误的助手。第一次给它项目资料，第二次带回测试结果，第三次继续修改。同一份工具说明、项目约定和历史对话，会反复出现在请求中。

普通问答的直觉

输入一次 → 得到一段回答

人容易只关注回答是否聪明、每秒输出多少字。

→
多轮任务的现实

反复带回历史 → 多次计算 → 验收

同一份上下文的重复处理成本，也会影响任务能否做得起。

评价模型完成多轮任务的效率，应在相同验收标准下，比较整个任务的总费用、总耗时和失败重试次数。这类任务会反复提交相同的项目资料和历史对话，因此，缓存能否复用、能省去多少重复计算，也会影响任务的整体开销。

03
小王 · 问

说“把模型已经读过的内容缓存起来”，我会想到保存原文，或者把上次的回答存下来，下次直接取用。但这里保存的却叫 K 和 V。

K 和 V 实际是什么，分别用来做什么？保存它们以后，模型下一步具体能少算哪一部分？

大王 · 答

模型处理一个已知 token 时，会在注意力层里生成供计算使用的数字向量。Q 用来查询，K 用来计算匹配程度，V 提供按权重读取的信息。当前 token 也会产生自己的 K/V，与已有 token 的 K/V 一起参与本层计算。[1]

模型处理一个 token 时使用的内部数值，称为模型中间表示（hidden state）；它还不是输出层给候选 token 打出的分数。

下面固定为同一次回答：假设用户输入只有 3 个 token，占序列位置 1～3；模型已经选出回答的第 1 个 token，占位置 4。现在把它送回模型计算，准备选出回答的第 2 个 token，也就是位置 5。

先分清：词表 ID、序列位置、模型层
token ID 是 token 在词表中的编号，用来查它的初始嵌入向量（embedding）。它不表示这个 token 排在输入的第几位。
Q₄、K₄、V₄ 的下标 4 表示序列中的第 4 位，不是词表 ID、层号或查询头号。同一层里，后面的查询可以读取这一位置的 K/V。
K4(2) 表示第 2 层、第 4 位的 K：下标是位置，括号内的上标是层号。图中省略层上标时，层号由“第 1 层”等标签给出；不同层的 K₄ 不是同一份数值。图示的位置与层号从 1 开始，引用代码从 0 开始的编号时会另行说明。
Attention(Q, K, V) = softmax(QKᵀ / √d) V

先计算当前查询与各个 Key 的匹配程度，再按权重汇总 Value。

一次调用通常先读入已给定的一整段输入（Prefill），再逐步生成新 token（Decode）。读入输入时可以批量、并行处理许多 token；生成时，处理当前已知 token 的结果用于预测下一个 token。缓存省去的是旧 K/V 的重复计算，后续读取和新内容的计算仍然存在。[1]

图中只展开一个注意力层。普通 Transformer 的不同层会分别产生自己的 K/V，这里省略了注意力头等维度。选出 token 5，不代表已经计算了它自己的 K/V。如果还要继续生成，token 5 会在下一轮被送回模型处理，再产生对应的 K/V。

下一次请求能否重新使用这些历史，还要检查前缀是否匹配、缓存是否可用。

04
小王 · 问

假设我提交 1,000 个已经确定的输入 token，再让模型生成 1,000 个新 token。前面的图说明，两者在被处理时都会计算 Q/K/V，可 API 通常给它们不同的单价。

输入和输出都要计算 Q/K/V，为什么前者可以成批处理，后者通常更贵？

大王 · 答

先看没有命中旧缓存的普通新输入。这些输入仍要计算 Q/K/V、读取上下文，并经过模型各层。要理解它为什么能高效处理，先解决一个疑问：后面的位置依赖前文，为什么多个位置仍能一起算？

把 1,000 个输入暂时缩成 A、B、C 三个已知 token；本问用 D、E、F 表示随后生成的回答 token。下面区分进入一层时的数值、该层生成的 Q/K/V，以及这一层算完后的数值；不要把它们当作同一个时刻的东西。

生成回答时，为什么不能照样提前算后面的 token？

下面把两种处理放在一起：输入 A、B、C 的内容一开始就已给定；生成时则要先选出 D，才能查 D 的 embedding，把它送回模型。两边都先生成本层 Q/K/V，再做注意力。

小王处理已知输入时，层与层之间有先后依赖，但同一层内部可以并行，是吗？

大王：是，但这里指多个位置一起做同一个步骤。本层先准备 Q/K/V，再计算注意力、完成后续处理；这些步骤之间仍有依赖。各步骤取得所需数据后，可以成批处理多个位置。下一层仍要接着上一层的结果计算。

小王那么，生成新 token 时，是不是连层内部也不能并行了？

大王：不是。图中的生成侧正在处理第 4 位 D，准备选出第 5 位 E。同一层里的多个查询头仍可以一起处理 D，各自使用自己的 Q。在一个头内，Q₄ 与不同 K 的匹配也可以并行；前馈等运算中的大量数字同样可以并行处理。

普通生成需要等待的是E、F 的内容依次确定：E 还没有选出来，就不知道该查哪个 embedding，不能提前处理 E。相比已知输入，少了同一条回答中多个新位置一起处理的机会，并没有失去当前 token 内部的并行能力。[40]

小王所以，生成 Q/K/V 不依赖历史信息，只有注意力计算才依赖历史 K/V，是吗？

大王：要区分“这一步直接读取什么”和“它的输入已经包含什么”。以输入 A、B、C 中的 C 为例：

第一层：C 用自己的 embedding 生成 Q/K/V，此时还没有通过注意力读取 A、B。随后，C 的第一层注意力读取 A、B、C 的 K/V；经过本层后续计算，C 的第一层输出已经可能受到 A、B 的影响。

第二层：C 使用自己的第一层输出生成新的 Q/K/V，因此这些数值已经间接受到 A、B 的影响。只是生成它们时，不需要先读取 A、B 的第二层 K/V，也不用等 A、B 做完第二层注意力。

不直接读取本层的历史 K/V，不等于不受历史信息影响。历史信息可以先进入上一层的输出，再影响这一层生成的 Q/K/V。[40]

模型先处理整段输入。为了生成回答的第一个 token，许多实现只取最后一个输入位置经过各层处理后的内部数值，再由输出层给词表中的候选 token 打分。前面的输入位置仍参与模型计算，只是不必分别计算它们各自的下一 token 预测分数。这里的词表分数（logits），是输出层对候选 token 的原始分数，尚未转成概率。[11]

下面回到原题的 1,000 个输入：D、E、F 仍表示回答 token，但它们在整条序列中的位置依次是 1,001、1,002、1,003；不再是三个输入简例中的第 4、5、6 位。

例如，GPU 把一块模型权重读入计算所用的高速存储后，批量处理时可以用它计算多个 token。单条回答逐步生成时，每一步新处理的位置较少，却仍要访问模型权重和历史 K/V，更容易花时间等数据。这里的权重读取主要发生在 GPU 的显存与计算单元之间，模型不会因此每步都从硬盘重新加载。[28]

批量处理没有把 1,000 个 token 的计算量变成一个 token 的计算量。它改变的是这些工作怎样安排，以及单位 token 的开销如何分摊。输出过程本来就在使用 KV 缓存；缓存省掉了旧位置的重复计算，却无法提前确定未来 token，也不能免除新一步的计算与历史读取。

输出还会让请求持续占用资源：越晚结束，相关状态就需要保留越久；继续生成也会增加新状态。服务端可以把多个用户的生成合成一批，但仍要兼顾显存容量和每个人的等待时间。

后面的推测解码，正是利用这个区别
推测解码先让较便宜的草稿模型猜出一小段 token，再把这些候选当作已知输入，交给负责最终回答的目标模型成批计算。不过，这次要给多个位置计算下一 token 的分数，才能逐项核验草稿，而不只是预测整段输入之后的第一个 token。

这里的“已知”，只是已经拿到候选的 token ID，不代表目标模型已经同意采用；目标模型可以先算出“假如接上这串候选，各位置会得到什么预测”，再决定接受哪一段。

02 / IDENTITY · 一步步拆到 token 级

整个前缀，究竟要不要“整个存下来”？

这里的核心区别，是前缀的身份与前缀的计算状态。把它们分开，hash、单 token 缓存和块缓存就能放进同一张图。

05
小王 · 问

比较“我 喜欢 苹果”和“我 讨厌 苹果”。假设这里的“苹果”是同一个 token，也处在相同的位置；变化的只有它前面的词。

既然当前 token 和位置都一样，为什么还不能直接拿上一次“苹果”的 K/V 来用？前文是怎样影响它的？

大王 · 答

比较两句中的第 3 个 token“苹果”。在标准模型的第一层、尚未读取前文时，相同 token 和相同序号可以得到相同 K/V。但第一层注意力分别读取“喜欢”与“讨厌”所在的前文，计算出的结果可能不同；第二层再用这些结果生成 K/V，就可能出现差异。

KVi(ℓ) = Fℓ(x1, …, xi; 模型与运行条件)

下标 i 表示 token 的序列位置，上标 (ℓ) 表示第 ℓ 个模型层；xi 是第 i 个 token。Fℓ 表示对应层的计算关系，它与用来查目录的 hash 函数是两件事。

因此，仅用 token_id 或 (token_id, position) 作为通用的高层 KV 缓存键，会把不同的上下文混为一谈。需要把此前的条件也区分开。

但这里还没有推出“缓存键必须把整段前缀明文存进去”。那正是下一个问题。

一个架构相关的细节
如果在某层注意力之前加入读取相邻 token 的模块，那一层的 K/V 会更早带入上下文。后文的 Engram 就属于这种情况。层号从 0 开始时，layer 1 是第二层；第二层出现 n-gram 注入，不能单独推翻“第一层在逐位置输入变换下可以相同”的条件判断。
06
小王 · 问

既然同一个 token 的 K/V 会受前文影响，那我能不能给不同的前文生成不同的缓存编号？这里用 A、B、C 分别代表一个 token。

比如，先给 A 生成一个编号；接着处理 B 时，把“A 的编号”和 B 一起生成新编号，用它代表 A→B；再处理 C 时，用“A→B 的编号”和 C 生成下一个编号。

然后用一张按编号查找的表，也就是 hash map，找到对应的缓存。这样，每个编号虽然很短，却已经考虑了此前的整段内容，不必在每个缓存条目里重复写一遍前文。

这种办法能不能正确区分不同上下文？如果可以，“必须包含整个前缀”指的是保存前文原文，还是保存能够区分前文的编号？

大王 · 答

可以。服务端先根据输入前缀和模型等条件生成缓存编号，再查找已经保存的 K/V，不需要把 K/V 重新算一遍，才判断能否复用。[2]

vLLM 的 hash_block_tokens 就把父块 hash、当前块 token 与附加身份信息一起交给 hash 函数。这与“parent_hash + current_token”的思想一致，只是它通常以块为单位。[3]

07
小王 · 问

既然能够为每个 token 位置建立缓存入口，为什么不这样做，让之前算过的相同前缀全部得到复用？

比如，上次处理了 1,000 个 token，这次前 999 个完全相同，只有最后一个变了。假设之前的缓存都还在，也能直接继续使用，那么为每个位置建立入口，就可以复用前 999 个，只计算最后一个。按每 16 个一组复用，却只能复用到第 992 个，还得把已经算过的 7 个重新算一遍。

这里想达到的 100%，只指那 999 个相同 token 全部复用；新内容仍需计算，本次全部 1,000 个输入的命中率仍是 99.9%。

为什么不把入口做得足够细，让已经算过的相同前缀达到 100% 复用？按组管理缓存究竟省下了什么，值得付出这些额外计算？

大王 · 答

可以这样做。入口更细能减少重复计算，也可能增加编号、查找和管理工作；是否划算，要比较两边的实际成本。

小王多建一些缓存入口，具体会增加什么工作？

大王：先算建立入口要花多少成本，再看这些入口能替后续请求省下多少计算。

而且，在“前一个编号＋当前内容”的链式 hash 方案里，后一个编号依赖前一个编号。第一次建立整条链时，不能简单地让所有编号同时生成。vLLM 的相关代码就是逐组生成，并把本组编号交给下一组使用。[13]

小王编号建好后，以后只查表，还会有什么开销？

大王：系统还要知道缓存在哪里、谁正在使用它，以及什么时候可以回收。

例如，两个请求同时使用同一份缓存。第一个请求结束时，系统不能把第二个请求还在读取的数据回收。因此，每次开始使用、结束使用，都需要更新相应记录。

vLLM 的缓存管理代码会逐个处理缓存块：命中后增加使用计数，请求释放时减少计数，并调整哪些块可以被回收。[13]

如果连实际管理单位也从 16 个 token 拆成 1 个，这类管理操作就会变多。高并发时，CPU 花在管理缓存上的时间，可能抵消 GPU 少算几个 token 带来的收益。

但要分清：只提高匹配精度，不一定需要把底层存储和管理单位也拆细。这几件事可以分别设计。

小王能不能保留逐 token 复用，同时少维护一些入口？

大王：可以。实际系统会改进数据结构，避免提前为每个位置建立独立条目。

例如，先把连续的 1,000 个 token 作为一段记录。下次请求与它共享前 999 个 token，就在第 999 个 token 后面把这段记录拆开。这样，仍然能准确复用前 999 个，却不必一开始就建立 1,000 个独立的树节点。

SGLang 的缓存树就有这种做法：节点可以保存一段连续内容，匹配结束在段内时再拆分；其普通 token 匹配路径支持单 token 精度。这里拆分的是组织缓存的记录，已有 K/V 数据可以继续使用。[5]

因此，工程上真正需要比较的是：更细的复用多省了多少计算，为此多付出了多少查找、管理和存储成本。最终要用同一批请求测量总耗时、内存占用和服务能力，才能判断哪种方案更合适。

把四件事分开
① 数值计算：许多 token 可批量计算。
② 物理存储：KV 可能被分配到页或内存池。
③ 查找粒度：按 token、缓存分组或前缀树路径查找。
④ API 缓存边界：服务商决定在哪些前缀结束处建立可复用入口。
它们是四件事，不是模型里的四个计算层。

有相同前缀，还差哪些条件才能命中？

缓存目录得找到它，数据得还在，而且留下来的状态必须足以从那个位置继续。API 的缓存点就处在这一层。

小王 · 问

我在 Claude 请求的一段资料末尾加上 cache_control，后面还会继续放本次的问题。这个位置被称为 breakpoint，有时又被译成“截断点”，听起来像是后面的内容会被截掉。

这个标记实际控制什么？它缓存的是被标记的这一段，还是从请求开头到这里的全部内容？后面的新问题还会正常处理吗？

大王 · 答

更合适的中文是缓存边界或恢复点。“截断点”容易让人误会后面的内容不再输入给模型。

把 cache_control 放在某个内容块上，表达的是：从整个有效提示的开头，到这个块结束的前缀，成为候选缓存范围。Claude 文档规定相关顺序为 tools → system → messages。[4]

多个缓存点可以对应不同稳定程度：工具和系统指令几乎不变，项目资料偶尔改变，对话不断追加。较长的入口失效时，较短的入口仍可能有效。但它们都表示“从开头到某处”，不会把后面相同的文本自动变成独立于前文的缓存片段。

09
小王 · 问

我连续三次提交同一份长资料，但分别问三个不同的问题。DeepSeek 不要求我手动标出资料在哪里结束，服务端需要自己决定保存哪些部分。

它怎样发现并保存这段共同的开头？相同资料从第二次就能复用，还是可能要等到后面的请求？

大王 · 答

先固定场景：A 是整份资料，B、C、D 是三个不同的问题。每次都从 A 开始，随后的问题被替换。

先分清：全局 K/V 与局部 K/V

有些模型会同时维护两种 K/V 缓存，这里讨论的 DeepSeek V4／V4.1 就属于这种情况。“全局”和“局部”说的是它们覆盖的上下文范围。

全局 K/V：让较早的内容仍可被读取

保留覆盖已处理长上下文的记录，供模型回看报告前面乃至开头的信息。这些记录可以压缩保存，也可以由多个模型层共用；“全局”不表示每一步都必须把所有记录读一遍。

局部 K/V：各层保留最近一小段状态

每个模型层保留自己为近期 token 算出的 K/V，用来读取当前位置附近的内容。最近这段 token 的范围叫作局部窗口。随着新 token 被处理，新记录加入，最早的记录从当前窗口移出。

在近期窗口内读取信息的计算，叫局部窗口注意力（Sliding Window Attention，SWA）。在同时使用两路 K/V 的层里，模型既读取局部窗口，也可以从全局记录中选取较早的信息。这样能兼顾长距离信息和各层近期的状态。[12][14]

各层可以保留相同范围的 token，但 K/V 来自各层自己的计算。共享的全局记录与这些局部状态也不是同一份数据，不能直接截取全局缓存的末尾，代替各层的局部缓存。[12][14]

已经算过 A，为什么还可能接不上 C？

API 文档直接说明，前缀保存规则受到 SWA 影响。关键在于：能识别相同前缀，不代表从那里继续计算所需的全部状态仍在。[6]

下面用一个局部窗口宽度为 4 的教学模型：资料 A 占第 1～4 个 token，旧问题 B 占第 5～8 个。看完 A+B 后，现在要从 A 的末尾改接新问题 C。

V4.1 报告 §3.2.1 回顾旧版 V4 的部署：全局 K/V 整段保留，局部窗口快照主要保存在输入结束和输出结束处。中间某个前缀的末尾，不一定有局部快照。[14]

结合报告与 API 示例，可以这样解释：先前缺少 A 末尾的局部恢复状态，需要补算；公共前缀被识别并保存后，后续请求才有对应的接续条件。这是机制解释，API 没有逐项公开线上内部过程。

V4.1 怎样改变这个约束？

报告 §3.2.2 的有界重放方案，在全局 K/V 可用、局部状态缺失时，只重新计算资料末尾的一小段来补回局部状态，降低了对长期局部快照的依赖。但这些 token 原先可能用过更早的计算结果；缺少那些结果，补出的状态未必与原来相同。[14]

小王 · 问

模型正在读入一份很长的资料。除了保存 K/V，注意力计算还要生成匹配分数，把分数变成读取权重，再算出从各条 V 取回的内容。

这些临时结果为什么也会占用大量显存？FlashAttention 怎样解决这个困难？

大王 · 答

先看困难：K/V 之外，还会产生两张很大的临时表

假设模型一次读入 10,000 个 token，先只看其中一层的一组 Q、K、V。把计算拆成几个独立步骤的做法是：

  1. 算匹配分数。每个输入 token 的 Q 与各条 K 按模型规则算出分数。把所有查询的结果排在一起，就得到一张分数表。
  2. 把分数变成读取权重。对同一个 Q 的分数取指数，再除以这些指数值的总和，让这一排权重加起来等于 1。这一步叫 softmax；不允许读取的未来位置会被排除。

    这是普通 Transformer 已有的步骤。后面的索引向量用于先筛选记录；入选后仍需重新打分，再用 softmax 算读取权重。

  3. 用权重取出 V 的贡献。把每条 V 中的数字乘以对应权重；再把各条 V 的第一个数字相加、第二个数字相加，依次得到输出中的每个数字。

如果实现先把完整方表存进显存，10,000 行、10,000 列就是 1 亿个数。按每个数 2 字节计算，一张表占 200 MB；若分数表和权重表各留一份，就是 400 MB。这是一个采用完整方表的存储算例：未来位置虽然不能参与读取，方表仍为它们留了位置；这里只计一层的一组 Q、K、V，MB 按十进制计算。

困难还不只是放不放得下，还包括数据在两处之间搬运。显存用来保存大量数据；计算时，要把需要的部分读入 GPU 芯片内部的高速存储，例如寄存器、片上 SRAM，供计算单元处理。

如果打分、softmax 和组合 V 分开执行，中间结果就可能先写到显存，下一步再读入芯片内部。下图用箭头把这条路径画出来。

FlashAttention：把一小块数据的计算连着做完

FlashAttention 是一种注意力计算方法。它把一小块 Q、K、V 读入芯片内部，让临时分数在那里继续用于后续计算，避免把完整分数表、权重表写到显存。对照下面两条路径，就能看出省在哪里。

选读：分块计算，softmax 为什么仍能得到原来的结果？

把规模缩成 3 个输入 token，只跟踪第 3 个 token 的 Q。假设三个匹配分数取指数后为 1、1、3，对应 V 为 0、0、10；本例每条 V 只用一个数字说明。

先不急着除以总和，保留“指数值总和”和“指数值乘 V 后的总和”：

  1. 第一块有第 1、2 条记录：指数值累计为 1 + 1 = 2，V 贡献累计为 1 × 0 + 1 × 0 = 0。
  2. 第二块有第 3 条记录：两个累计量分别更新为 2 + 3 = 5 和 0 + 3 × 10 = 30。
  3. 所有块处理完：统一相除，得到 30 ÷ 5 = 6。这与权重 1/5、1/5、3/5 分别乘 V 后相加的结果相同。

不能把每块独立计算的答案直接平均：第一块是 0，第二块是 10，平均得到 5。那样会丢掉两块应占的权重。

实际代码还要处理一件事：指数太大，怎么办？

分数很大时，取指数可能超过计算机能表示的范围。做法是先减去目前见过的最大分数，再取指数。这相当于把指数值同时缩小相同倍数；V 的贡献也缩小同样倍数，最后相除的结果不变。

如果后一个块出现了更大的分数，旧累计结果也要一起调整。上例第二块到来后，把指数值统一缩小 3 倍：第一块的累计 2 变成 2/3，第三条的 3 变成 1，V 贡献总和变成 10。最后 10 ÷ (2/3 + 1) = 6，结果仍然一样。

所以，实际实现为每个查询保留最大分数、指数值总和、V 贡献累计，每来一块就更新它们，最后完成除法。数学结果等价；有限精度下，计算顺序改变仍可能带来舍入差异。[49]

选读：把上述步骤写成更新公式

m 是已处理记录的最大匹配分数，ℓ 是减去这个最大值后得到的指数值总和，z 是用这些指数值乘 V 后的累计结果。新块的分数为 sᵢ，对应的 V 为 vᵢ：

m′ = max(m, max s)
α = exp(m − m′)
ℓ′ = αℓ + Σ exp(sᵢ − m′)
z′ = αz + Σ exp(sᵢ − m′)vᵢ

α 把旧累计结果换到新最大值对应的尺度；所有块处理完后输出 z/ℓ。开始时 m = −∞、ℓ = 0、z = 0。只累计允许读取的位置；被因果遮罩排除的未来 token 不参与。

它省掉了什么，仍然要做什么？

省掉的是两张完整临时表的存储，以及围绕它们的显存读写。减少这些搬运可以提高速度，但这不意味着删掉历史 K/V，或跳过原本应参与的 Q、K 匹配计算。

方法主要省在哪里仍然需要什么
前缀缓存相同输入的 K/V 不必重新生成新查询仍需读取历史并计算
PagedAttention无需预留一整块连续显存，减少空间浪费每条 K/V 本身仍要占用空间
FlashAttention不把完整分数表和权重表存进显存仍读取参与本次注意力计算的 K/V

这些技术可以配合使用。FlashAttention 的公开缓存接口可接受页表；具体实现是否同时支持分页、量化和窗口注意力，仍需分别核对。[48]

大王 · 答

查询头的数量，不一定等于实际保存的 K/V 组数。先固定一个模型层，按单个 token 计算缓存大小：这个例子有 8 个查询头，每 4 个头共用一组 K/V，共 2 组。

假设每个 K 和 V 都各有 4 个数，每个数占 2 字节：一组 K/V 占 (4＋4)×2 = 16 字节，两组共 32 字节。再按保留的 token 数、各层的实际形状累加，就得到整份缓存的基本大小。

多个查询头各留一组 K/V，是多头注意力（MHA）；所有查询头共用一组 K/V，是多查询注意力（MQA）；在两者中间，几组查询分别共用 K/V，是分组查询注意力（GQA）。这是头之间的共享，不是请求之间或层之间的共享。[39]

小王多个查询头共用一组 K/V，这种共享发生在同一个 head 内吗？是不同位置的 token 的 Q 复用历史 K/V，还是同一个 token 在不同 head 里的 Q 共用 K/V？

大王：这里指同一层中，不同查询头之间共享 K/V。固定同一个 token 来看，它在不同头里产生各自的 Q，这些 Q 可以共同读取一套历史 K/V。

例如已经有 5 个输入 token，下面只看第 5 个 token 在这一层的计算：它产生 8 份 Q，各查询头一份。头 1～4 共同读取 A 组历史 K/V，头 5～8 共同读取 B 组；每组都仍保存第 1～5 个 token 各自的 K/V。

如果忘记了层与头的关系，可以回看 FIG 01「一个层里有多个头；层与层依次传递结果」。

“一组 K/V”是一套按 token 位置保存的历史记录。A 组中仍有第 1 个 token 的 K/V、第 2 个 token 的 K/V，一直到第 5 个 token 的 K/V。它们共同供头 1～4 使用，并没有把这 5 个 token 合成一对 K、V。

小王那同一个头中，不同 token 的 Q 读取相同的历史，又属于什么？

大王：这也会发生。例如头 1 中，第 4 个 token 的 Q 和第 5 个 token 的 Q，都能读取第 2 个 token 已有的 K/V。这种沿 token 序列的复用，在普通 MHA 中本来就有；GQA、MQA 还让不同查询头共用同一套历史。[39][40]

小王 · 问

我看到某个缓存标成“4 bit”，以为内存一定只剩原来的四分之一。但程序里还有 scale、解包和临时张量；有时换了格式反而更慢。

KV 量化怎样真正省空间？为什么存得更小仍可能跑得更慢？

大王 · 答

把每个数字用更少的位保存，叫量化。直觉上像把精细刻度换成较少档位：存的是档位编号，还要知道这一组数字的量级。恢复后通常只是原数的近似值。

例如，这一组每档代表 0.1：原数 0.32 可以记成档位 3，读取时算 3 × 0.1 = 0.3。少存了位数，也丢掉了一点精度；“每档 0.1”这个缩放系数（scale）也必须保存。

小王那缓存压成四分之一，生成就能快四倍吗？

大王：不能。只有原本受缓存读取带宽限制、压缩路径被内核有效利用，而且新增开销较小，少搬数据才可能转成延迟收益。上下文较短、显存已足够时，量化反而可能更慢；应把恢复工作区也算进峰值内存。[41]

小王K 和 V 都是数字，为什么有人用不同量化方式？

大王：K 的误差先改变匹配分数，再通过 softmax 改变读取比例；V 的误差直接进入汇总结果。因此，两者可以采用不同的量化方式，是否合适要看模型和任务。[42]

如果程序把低位数据全部还原成较高精度张量后再保存，就不能只按压缩文件的大小估算内存。附录 C 会分别记录打包数据与缩放系数的实际字节数。

小王 · 问

YOCO 的全称是 You Only Cache Once，直译是“只缓存一次”。但一个 token 仍然要经过模型的多层计算，这个“一次”到底在数什么，很容易混淆。

它是让一个 token 只计算一次，还是让多个层共用一份历史 K/V？哪些层共享，前面的层还需要保存自己的状态吗？

大王 · 答

YOCO 是一种大语言模型架构。它让后半多个层共读前半生成的全局 K/V，减少重复保存，并让部分输入位置省去后半计算。代价是后半各层不再独立生成各自的全局历史；模型需要按这种结构训练。[7][8]

原论文把模型分成前半的 Self-decoder 和后半的 Cross-decoder：前半先得到上下文表示，由它生成共享的全局 K/V；后半各层通过各自的查询读取这份记忆。[7]

小王后半的多个模型层共享全局 K/V，它们还有各层自己的局部 K/V 吗？

大王：对于原始 YOCO，后半层没有另外保存各层私有的局部 K/V。它们用自己的 Q，读取前半统一提供的全局 K/V。

前半则仍需要保留自己的状态：采用滑动窗口时，各层保存最近一段 token 的 K/V；采用递归变体时，保留的是不断更新的状态，不能直接称为“最近若干 token 的局部 K/V”。[7][8]

没有单独的局部缓存，不意味着看不到最近的 token。例如，共享全局缓存包含第 1～1,001 个 token 的记录，那么最近的第 990～1,001 个也在其中，后半层照样可以读取。

小王但是逐步生成下一个 token 时，后半各层仍有自己的查询、注意力和前馈计算。这样不是又有了自己的局部 K/V 吗？

大王：有自己的 Q 和后续计算，不等于生成了自己的 K/V。普通 Transformer 通常每层都生成自己的 Q、K、V；YOCO 改变了这个安排：后半各层生成自己的 Q，K 和 V 由前半统一提供。注意力需要使用 Q、K、V，但不要求三者都由当前层生成。

沿用 4 个模型层的例子，先看首次处理 1,000 个已知输入 token，再看怎样逐个生成回答。两个阶段的区别，主要在于哪些位置还需要经过后半层。

参考代码中，后半注意力模块有生成 Q 的 q_proj 和处理结果的 out_proj，K、V 则从外部传入。[8]

后文的 DeepSeek V4.1 Flash 采用了另一种组合：共享全局 K/V，同时维护各层自己的局部窗口 K/V。它的参考代码另设 window_kv_cache，为各层生成并保存局部记录。它有局部缓存，是因为架构安排了这条计算与保存路径，不能仅凭“后半层还在做注意力和前馈计算”就推断出来。[12]

这个理解对吗？缓存、读取和逆旋转，到底怎样衔接？

大王 · 答

“旋转后的 K，加上没有做这次旋转的 V”是常见的缓存形式；但读取后并不先对 K 做逆 RoPE。当前 Q 按自己的位置旋转，直接与缓存 K 比较。文中那道逆旋转发生得更晚：先把读出的信息按权重相加，再处理得到的新结果。

先澄清“共享”：多个头或层共用一组 K/V，不等于 K 和 V 本身是同一个向量。这问讨论上一问的后一种设计。旋转位置编码（RoPE）让位置参与 Q、K 的匹配；这种特殊设计又把已旋转的同一份向量拿来当 V。

“V 没有位置信息”也要收窄为“V 没有施加这一层的 RoPE 旋转”。V 来自模型的中间计算，可能已经包含前面层形成的位置相关信息；未做这次旋转，不等于完全没有位置信息。

对照代码：缓存写入、乘权重相加、输出逆旋转

Llama 的常见实现先对 Q、K 调用 apply_rotary_pos_emb，再将 K、V 交给缓存；所以存入的是已经旋转的 K，以及没有做这次旋转的 V。[11]

文中共享向量的实现先旋转并保存 kv。随后 sparse_attn 用它与 Q 算分数，又用同一份数据完成“各乘系数，再逐项相加”。最后才对这份输出调用 apply_rotary_emb(..., inverse=True)。[12]

匹配分数 = 当前旋转后的 Q，与缓存 K 作点积
读取权重 = 把匹配分数转换成每条记录的系数
读出结果 = 每条缓存向量乘自己的系数，再把同一维度的数相加
后续输入 = 对读出结果的 RoPE 部分，按当前查询位置逆旋转

这是按相应方式设计和训练的模型，不是给任意模型合并 K、V 就能直接得到同样的效果。num_key_value_heads = 1 也只说明 KV 头少，不能单独证明 K 与 V 是同一个向量。

我们通常在旧对话后追加新内容，把完整历史一起发给模型。

既然模型已经收到这些信息，为什么生成下一个 token 时，还要筛选历史？

大王 · 答

因为“历史都可以使用”和“这一步让哪些历史参加计算”是两回事。

假设对话没有被截断或替换成摘要，你提交的完整历史都属于本次上下文。模型会为这些输入生成 K/V，或者复用已经保存的 K/V。

但是，缓存只省掉了历史 K/V 的重复生成。每生成一个新 token，模型仍要根据当前计算产生 Q，用它寻找需要的历史信息，再把读出的信息组合起来。

如果采用完整注意力，就让全部允许访问的历史 K/V 参与这个过程。历史很长时，每一步都要读取大量数据、进行大量计算，即使显存放得下，也不意味着读得快。

DeepSeek V4.1 Flash 的一种做法是：先用较短的索引向量给历史记录评分，选择一部分全局 K/V，再让主注意力读取这些记录，同时读取近期局部窗口的 K/V。[14]

第一个数乘 0.6，第二个数乘 −0.2，再相加。
2 × 0.6 + 1 × (−0.2) = 1.0

2、1 来自这次读到的内容；0.6、−0.2 是训练后保存在模型里的参数。换一条记录，如果输入变成 [5, 3]，同一规则就算出 5 × 0.6 + 3 × (−0.2) = 2.4。内容和计算结果变了，普通推理时的参数没有变。

大王 · 答

可以给索引器单独设置一个训练目标，让它学习应该怎样分配分数。先分清两个都可能被叫作 mask 的操作：

  • 遮住文字，再预测原文：例如把“小王住在北京”改成“小王住在 [MASK]”，要求补出“北京”。这是掩码语言建模，BERT 使用过这种任务。[38]

V4.1 Flash 的语言主体采用逐步预测后续 token 的因果模型。筛选器怎样学会选历史，是另一个需要说明的训练问题。[14]

先有已经训练过的 V3.1-Terminus 基础模型，再加入索引器；主模型只在索引器预热期间暂停更新，后面还会继续训练。[37]

主注意力的参照又是怎么来的？主模型此前已经接受文本预测训练：根据前文预测后续 token，用预测与正确文本的差距调整参数，其中包括注意力里的参数。索引器利用这套已经学到的读取方式作为参照，不需要人工给每条历史标注“相关／不相关”。

V3.2 后续进入真正的稀疏训练时，主模型继续按文本预测误差调整，索引器则按选中记录上的分配差异调整，两套训练信号分开。训练完成后，实际使用时先让索引器选记录，再做主注意力；不需要每次回答都先完整计算一遍主注意力来当参照。[37]

这里的“相关”，是索引器在近似主注意力对历史的选择。权重高不等于已经证明该记录对正确答案必不可少；筛选有没有漏掉关键信息，还要用任务结果检验。

所以，额外的筛选训练目标在 V3.2 就已明确存在，它不是一种新的 mask 补词任务。对于 V4.1 Flash，公开报告说明了索引器参数的优化与梯度汇总，但没有同样完整地给出索引器训练误差的定义。可以确认它参与训练，不能据此认定其完整训练方法与上图相同。[14]

小王 · 问

按普通的逐 token 生成顺序，第 9 个 token 已在上一步选出。现在把它作为新输入送进模型，准备生成第 10 个 token；前面第 1～8 个位置的 K/V 仍有效地保存在缓存里。

假设某一层的全局注意力选中了位置 2、9 的记录。

没选中的第 1、3～8 条要重算吗？第 2、9 条又怎样参与生成第 10 个 token？

大王 · 答

第 1、3～8 条不需要重算，第 2 条也不需要重算。第 2 条从旧缓存直接取出；第 1、3～8 条继续保留，只是不参加刚才这一层的全局主注意力计算。

第 9 条是本轮为新输入准备的 K/V。第 9 个 token 上一步刚被选出，现在才作为输入参与这一轮计算。因此，这里的第 9 条属于本轮新增的状态，不能与前面第 1～8 条旧缓存混为一谈。

发起查询的是第 9 个位置在当前层产生的 Q₉。它读取所选记录，影响第 9 个位置接下来的内部数值；模型最后根据这个位置的计算结果，选出第 10 个 token。

读出的信息不是直接变成文字。模型先把注意力结果作相应变换，与第 9 个位置已有的信息合并，再经过前馈网络和后续模型层。最后，输出层才给词表中的候选 token 计算原始分数，也就是词表分数（logits），随后选最高分或按概率采样，确定第 10 个 token。[12]

在生成同一个 token 的过程中，不同层就可能读取不同历史。第 9 个位置的内部数值经过前面的层后发生了变化，后面的层据此产生自己的查询，可能给历史记录打出不同分数。图中某个后续层改选第 5、8 条时，仍在为生成第 10 个 token 做计算，并没有开始生成第 11 个。

V4.1 并非每层都重新筛选。其中，共用历史缓存、根据本层索引查询重新筛选的方式叫 Reindex；连同前面选好的名单一起沿用的方式叫 Reuse。前者可以改变读取名单，后者省下再次筛选的工作。[14]

沿用名单，也不等于沿用读取权重。例如两个层都读取第 2、9 条，前一层可能分配 75%／25%，后一层可能分配 40%／60%。名单相同，但每层仍用自己的主注意力 Q 与 K 匹配，因此算出的读取比例和汇总结果可以不同；这些比例是教学举例。[12]

不连续的记录可以直接读取。位置 2、9 仍然是原来的位置，不会被重新编号成 1、2。使用第 2 条已经算好的结果，不需要把产生它时用过的前文再算一遍；读取名单也没有删除或改写原历史。

索引器为了决定选谁，可能重新给旧索引特征打分；后续层若选中第 5 条，就直接读取对应的有效缓存。重新打分和改变名单，都不等于重新生成旧 K/V。

大王：具体工具确实可以等需要时再找。Pi 提前放的是一个永远不激活的占位项，目的是让服务端的延迟加载配套提示从第一轮就存在。

小王为什么还需要“工具提示”？结构化配置就意味着必须提前启用延迟加载吗？

大王：工具提示向模型说明本次有哪些工具、参数怎么填、调用怎样表达。Anthropic 把工具定义、配置和系统指令等组装成模型输入，属于它采用的接口实现。JSON 本身也能提供工具定义；需要传递这些信息，不能推出“首次启用延迟加载必须改动前缀”。[34]

公开资料没有给出那段延迟加载配套提示的全文，也没有解释为何要在首次启用时改变前部。当前接口文档说明延迟工具定义在后续位置展开、可以保留缓存，但未列出 Pi 注释中的首次启用例外。这里可以说明 Pi 的处理动机，不能将其写成当前所有接口的必然行为。[31]

小王如果现在自己设计 Agent，有没有比提前占位更好的方案？
更优先的设计：固定调用入口，具体工具按需发现
对工具种类经常变化、又希望保持旧前缀稳定的 Agent，固定搜索／执行入口是更优的设计方向。模型始终通过同一组入口办事，具体工具的用法通过后续消息提供，不需要每发现一个工具，就把它新增为模型服务的原生工具。

继续用 log_query 举例。第一轮只提供两个固定入口：search_tools 负责返回工具名、用途和参数格式；call_tool 负责检查参数并执行指定工具。在同一会话中，这两个入口的名称、说明和参数格式都保持不变。下面是教学接口的调用示意。

需要查日志时，模型先通过固定入口搜索：

search_tools({query: "读取测试日志"})

Agent 在后续消息中返回 log_query 的用途及 run_id 等参数说明。模型读懂后，再通过另一个固定入口调用：

call_tool({
  name: "log_query",
  arguments: {run_id: "run_42"}
})

这里的 log_query 是传给 call_tool 的参数；模型服务看到的工具入口仍是原来的两个。实际查询由 Agent 程序执行，结果继续追加到后续消息。更换具体业务工具时，只要入口定义保持稳定，就不必触发服务端的首次 defer_loading 路径，也不需要为这条路径预放占位项。

这类方式已有实际实现：Cloudflare 的 API MCP 服务通过 search 查询接口用法，通过 execute 运行调用代码；完整接口目录留在服务端，模型按需取得相关部分。它采用代码执行入口，与上面的通用 call_tool 示意不同，但共同点都是少量入口保持稳定，具体操作按需发现。[35]

这里比较的是对工具变化的控制能力：固定入口减少了对平台原生动态工具机制的依赖。它仍然需要按需提供工具信息，执行程序也要负责参数校验、权限和错误处理。这不等于已证明它在所有任务的费用、速度和正确率上都优于原生延迟加载。

小王 · 问

假设模型刚读完一段很长的上下文，随后要等一个六分钟的测试。如果服务端缓存五分钟后过期，测试结束时，旧输入可能又要重新计算。

Pi 怎样避免等待工具时缓存过期？为了保住缓存，多发一次请求划算吗？

大王 · 答

Pi 会在缓存预计过期前，尝试重放原来的模型请求，并把输出上限设为 1 个 token。这一步叫缓存保活：通过再次使用原来的输入，尝试让已有缓存继续可用。返回内容不加入聊天，但请求产生的用量会计入会话费用。[21]

例子：缓存有效期五分钟，测试需要六分钟
满足保活条件时，Pi 大约在第 4 分 30 秒发出一次刷新请求，希望测试结束后的下一轮还能读取旧缓存。它付出一次刷新费用，换取避免重新处理长输入的机会。

0.86.0 加入的这项功能，按默认规则这样工作：

  • 默认在任务运行期间保活。任务结束后停止；选择 idle 模式，才会在任务之间的空闲期继续尝试。
  • 先估算是否值得。模型需要提供可用的缓存寿命信息，请求也必须能安全重放；估算的净节省至少达到 0.05 美元，才会刷新。
  • 不会无限刷新。从原来的真实请求开始计时，运行期间最长保活一小时，空闲期最长三十分钟；如果定时器延误、错过安全刷新时间，就停止，避免为了保活反而重建过期缓存。

小王 · 问

我通过 API 做一个代码助手。它会临时加载工具，等待测试运行，也会在对话太长时生成摘要。

哪些操作可能让旧缓存失效？我应该先检查哪里，怎样确认改动让整个任务更省钱、更快，并且没有影响任务完成？

大王 · 答

通过 API 开发 Agent 时，你主要能调整输入组织、工具加载、对话摘要和请求安排，也能选择模型与服务。缓存存在哪里、怎样传输、模型内部怎样共享 K/V，通常需要服务提供者或自行部署模型的人处理。具体见缓存的存放与回收。

先检查实际发送的内容

把相邻两轮实际提交的工具定义、系统指令和消息展开比较，标出最早变化的位置。聊天界面看起来相同，不代表提交的内容相同：例如，Agent 可能每轮重写工具目录，或在输入开头插入新的时间。

固定资料尽量保持原样，新问题和工具结果按发生顺序追加；同一份资料用于回答不同问题时，把固定资料与变化的问题分开，按所用服务的规则设置缓存。只固定本来就不需要变化的内容。项目代码和要求已经变了，就应更新信息，不能为了命中缓存继续提供旧事实。

场景在自己的 Agent 中检查什么
临时加载工具是否重写了开头的工具目录？能否改用定义稳定的搜索／执行入口？若采用平台原生动态工具机制，再核对后续展开与首次启用的行为。
工具返回大量日志或明细原始结果有多大？实际交给模型多少？能否先筛选、保存全文，再按需读取？
生成并使用摘要分开观察生成摘要这一轮、替换后的第一轮、随后几轮的输入量、缓存用量、费用和任务表现。
等待长时间测试下一轮开始时缓存是否仍有效？保活增加的费用，能否被后续节省覆盖？

记录用量，按现象排查

记录每次请求的用途、输入量、缓存读取与写入量（接口提供时）、输出量、费用和耗时。不同接口的同名字段可能含义不同，要按对应说明记录。

查看 Claude 与 DeepSeek 的具体用量字段
Claude · 输入总量包含三部分
read  = usage.cache_read_input_tokens
write = usage.cache_creation_input_tokens
fresh = usage.input_tokens

total_input = read + write + fresh
hit_ratio = read / total_input if total_input else 0

Claude 的 input_tokens 不包含上述读缓存和写缓存部分。服务端工具或多轮汇总还应对照相应的用量记录。[4]

DeepSeek · 按命中与未命中统计
hit  = usage["prompt_cache_hit_tokens"]
miss = usage["prompt_cache_miss_tokens"]

hit_ratio = hit / (hit + miss) if hit + miss else 0

字段定义来自 DeepSeek 上下文缓存文档。[6]

汇总命中率时，把全部请求的命中 token 数相加，再除以全部输入 token 数；不同长度请求的命中百分比不宜直接做简单平均。

旧对话从缓存读取，新增对话写入缓存，是正常情况。需要区分正常的新增写入和旧内容未能复用，再按下面的现象排查。[4]

看到的现象优先检查什么
旧历史没有读缓存，同一大段内容反复写入请求前部是否被改动？对于同一份资料的不同问题，是否在固定资料末尾留下了可复用的缓存位置？追加消息后，上次写入的位置是否仍在服务的查找范围内？
只命中前面很短一段最早变化的内容在哪里？系统指令、工具目录或项目资料是否被重排或改写？
相同内容仍未命中是否达到服务要求的最短缓存长度？首轮缓存是否已经可用？间隔是否超过有效期？是否换了模型、API 服务或工作区？
命中很高，但窗口仍迅速变满是否一直携带已经用完的工具结果？哪些证据必须保留，哪些可以归档或摘要化？命中的 token 仍占窗口。
命中很高，但任务仍然慢分别计时：等待模型开始回答、生成回答、运行工具。先找出哪一段最耗时，再决定改哪里。

把整个任务的费用算全

把主 Agent、子 Agent、摘要、保活和失败重试产生的请求，全部计入同一个任务。单独看主对话的费用，可能漏掉为了优化它而增加的开销。各项费用按所用服务的实际计费规则计算，包括适用的缓存读取、写入、存储和输出费用。

99% 命中，也可能更贵
在同样完成任务的前提下，100 万输入 token、99% 命中的方案，可能仍比 1 万输入 token、0% 命中的方案更贵。提高百分比不等于减少绝对成本。没有必要为了命中率，反复塞进任务用不到的材料。

用相同任务比较改动前后

用同一组任务和同一套完成标准，比较改动前后。先固定模型，每次只调整一类策略；分别观察首次使用、连续对话和长时间等待后的表现，再汇总完整任务的结果。

要比较的结果用来回答什么
任务通过率是否仍然把事情做对？
整个任务的总费用包括额外请求之后，究竟省了多少钱？
从开始到完成的时间用户实际少等了多久？同时列出多数任务和较慢任务各要多久。
缓存用量和各阶段耗时收益或损失发生在哪里？

还可以用这组任务的全部费用 ÷ 通过验收的任务数比较平均完成成本，但必须同时列出任务通过率。API 没有提供的缓存体积、内部恢复时间，就标为无法直接测量，不把估算当作实测。

如果更换了模型或服务，也用相同任务重新比较完成质量、费用和时间。

09 / SPECULATIVE DECODING · 先猜一段，再核验

生成要一步接一步，为什么还可以批量核验？

从草稿交付、逐层计算到核验与回退，最后比较加速条件及它与 FlashAttention 的分工。

29
小王 · 问

模型正在继续同一段回答，通常要算一步、选出一个 token，再算下一步。推测解码却多安排了一个“先猜”的步骤。

什么是推测解码？多做了一份草稿，为什么反而可能更快？

大王 · 答

先用计算较便宜的方法猜一串候选，再由真正负责回答的目标模型核验。这种生成方式叫推测解码（Speculative Decoding，也叫投机解码）。下面用一个较小的草稿模型，帮助目标模型生成后续内容。

30
小王 · 问

草稿已经猜出 A、B、C、D。我会以为，目标模型直接拿草稿算好的 Q/K/V，判断 C 该不该改成 X，所以才能一起核验多个位置。

草稿交给目标模型的，到底是 token，还是已经算好的 Q/K/V？

大王 · 答

本章使用两个参数不同的独立模型。草稿提供候选的 token ID（词表中的编号）；目标模型查自己的嵌入向量（embedding），用自己的参数重新计算 Q/K/V。随机采样时还需要草稿的概率，供后续决定接受与补抽；这也不是把草稿 K/V 当作目标模型的缓存。

本例按位置保留完整历史 K/V。固定同一个起点：第 1～9 个 token 已确定，目标模型的 K/V 缓存到第 8 位；第 9 个刚选出，还没送回目标模型。草稿据此给出第 10～13 位的 A、B、C、D。

普通生成要等目标模型选出下一个 token，才知道下一轮输入什么。这里草稿已经先后给出 A、B 等候选，目标模型可以先计算“如果这段输入是 A、B……，各位置会得到什么结果”。若前面的候选被拒绝，依赖它的后续结果就不能接入最终历史。

31
小王 · 问

把草稿当作输入，目标模型就能批量处理。但读完普通提示词后，通常只需最后一个位置预测回答的第一个 token；核验草稿却要检查好几个位置。

两种处理分别需要哪些词表分数？核验 C 为什么要用 B 的输出？

大王 · 答

多个位置参与模型计算，与多个位置都输出预测，是两件事。模型最后一层的中间向量还不是词表分数；选定位置的向量送入输出层，才得到各候选 token 的原始分数，也就是 logits。

支持相关选项的实现会设置 logits_to_keep = candidate_length + 1，取得候选数量加一份预测。批量读入并不意味着只取最后一份预测；输出层要处理更多位置，最后未被采用的候选也可能已经花掉计算。

这里的词表分数用于选择下一个 token；注意力匹配分数用于当前模型层怎样读取历史。它们不是同一组分数。

32
小王 · 问

前面的例子让目标模型每次都选最高分的 token。现在改为按概率抽取，同时仍想让较便宜的草稿模型提前提出候选、减少等待。我们希望加快生成，但保留目标模型原本的选择规则。

随机采样时，怎样核验草稿，才能保持目标模型原来的抽取概率？

大王 · 答

先拿掉草稿：目标模型原本怎样选？

前文已经确定，现在只选紧接着的一个 token。目标模型先给词表中的候选打分，再根据本次采样设置，得到各个候选被选中的概率。

贪心选择每次都取概率最高的候选，前面 A、B、C 改成 X 的例子采用的就是这个设定。随机采样则按各自的概率抽取：概率较高的更容易被选中，其他候选也有机会。本问讨论的是后一种方式。

20% 说的是哪个机会？

为便于推演，假设这个位置只有甲、乙、丙三个候选 token。它们是同一个位置的三种备选，不是连续三个 token。下面的概率是教学设定。

候选 token目标模型的抽取概率
甲20%
乙50%
丙30%

按最高分选择就会选乙；按概率抽取，这一次也可能选中甲或丙。20% 指的是：固定同一段前文、同一个模型和相同采样设置，甲在紧接着的这个位置被选中的机会。

它不是“甲有 20% 的概率是正确答案”，也不要求“一段 100 个 token 的回答里必须有 20 个甲”。一旦选出一个 token 并继续生成，前文就变了，下一位置的概率会重新计算。

加入草稿后，概率可能变了

为了减少等待，先让较便宜的草稿模型提出候选，再由目标模型成批核验。两个模型的参数不同，即使读取同一段前文，也可能给出不同的概率：

候选 token目标模型原本的概率草稿提出它的概率
甲20%60%
乙50%30%
丙30%10%

如果草稿提出什么就采用什么，最终选择会跟着右列走。例如，甲被选中的机会会从目标模型原本的 20% 变成 60%。这样虽然利用了草稿，却也改变了最终的生成规则。

核验要保住什么？

我们要利用草稿提前提出候选，但最终仍按目标模型的 20%、50%、30%来选择。因此，程序需要三个步骤：

  1. 草稿按自己的概率提出一个候选。
  2. 程序结合两个模型给出的概率，决定接受还是拒绝这个候选。
  3. 如果拒绝，再按专门修正过的概率补选。

这里的“校正”调整的是接受与补选的规则，不需要重新训练或修改两个模型的参数。下面沿用表里的数字，具体算一遍：草稿提出的候选保留多少，被拒绝后又怎样补选。[54]

小王如果换成目标模型给甲 60%、草稿模型给甲 20%，两者相除就是 3。这不是超过 100% 了吗？甲是不是一定会被接受？

大王：是的。当草稿这次已经提出甲时，程序一定接受它。接受概率最多是 1，也就是 100%；比值超过 1，就按 1 处理，不会出现“300% 的接受概率”。

计算时始终用目标概率除以草稿概率，再取这个比值与 1 中较小的那个：接受概率 = min(1, 目标概率 / 草稿概率)。本例是 60% ÷ 20% = 3，实际接受概率取 100%。

说的是哪件事本例的概率
草稿提出甲20%

通过“草稿提出并直接接受”这条路径，最终选中甲20% × 100% = 20%

“提出甲就必接受”，并没有让最终结果全部变成甲。草稿本来只有 20% 的机会提出甲，这条路径只能贡献 20% 的最终概率。目标模型希望甲最终占 60%，还差的 40 个百分点，会通过其他候选被拒绝后的补选补回来。[54]

前面的图采用相反的给定概率：草稿给甲 60%，目标只给甲 20%，所以接受概率仍是 20% ÷ 60% = 1/3。改变的是两边给定的概率，除法顺序不变。

小王 · 问

回到前面出现拒绝的例子：草稿模型猜出 A、B、C、D；目标模型核验后接受 A、B，在 C 处出现分歧并改选 X，C 后面的候选 D 本轮不再采用。

已经算出的候选 K/V 留哪些，刚选出的 X 又在哪里？

大王 · 答

前缀缓存与推测解码可以配合：前缀缓存复用已经确定的旧输入状态；推测解码尝试更快地确定后面的新内容。带局部窗口或递归状态的模型，还要能正确恢复被撤回的状态，不能默认所有实现都只需把 K/V 尾部截短。

小王 · 问

目标模型仍要算候选的注意力和词表分数，还可能算了最后没采用的 C、D。为什么增加这些工作仍可能更快？“一块数据供多个位置使用”，听起来又像 FlashAttention。

推测解码省的是哪些等待？它和 FlashAttention 分别改变什么？

大王 · 答

算术运算量与等待时间不必同步变化。批量核验让同一批读入的模型参数服务多个位置，也可能用上原本没充分利用的计算能力；草稿、更多位置的预测和拒绝掉的计算则是额外开销。

小王草稿已经给出 A、B、C、D 四个连续候选，目标模型可以把它们作为同一批输入，在每一层里成批计算。这样，读入的一块模型权重就有机会供多个位置使用，而不用像逐个生成时那样，反复为下一步读取数据。

这是不是能减少 GPU 显存与芯片内部之间的数据搬运？FlashAttention 也是把计算分成小块，让读入的数据在芯片内部接着使用，减少显存往返。它们省掉的是同一种开销吗？推测解码算不算 FlashAttention 的升级版？

大王：推测解码确实可能减少一部分重复的数据读取，但它与 FlashAttention 优化的是不同环节，不是后者的升级版。这里比较的是 GPU 显存与芯片内部高速存储之间的数据搬运。

设计描述

  • 每 16 个 token 一块，只缓存写满的块。
  • 块编号由“前一块编号＋本块 16 个 token”的 hash 得到；第一块的前序编号由模型名和数值精度生成。
  • 新请求从第一块逐块查找，遇到第一个缺失就停止，后面的 token 全部现算。即使全部找到，也至少留最后一个 token 现算。
  • 每块记录有几个请求正在使用。容量满时，从没人使用的块里淘汰最久未使用的一块。登记或命中一串块时，从前到后依次标为刚使用过。

正常前缀复用在数学上等价。这里固定模型权重、位置规则与精度，且只比较题设中匹配正确的前缀。因果注意力不能读取未来位置，所以位置 i 在各层的 K/V 由第 1～i 个 token 及相关配置决定，不会因后面追加什么而改变。

这组 fp32 记录把差异定位到后 30 个 token 的计算路径，而不是缓存表里的前缀数据：

大王 · 问题 4 参考解析
先证明贪心选择何时不变

把不用缓存时的第一名记为 a，其他候选记为 j。a 比任何 j 至少高 m。另一条路径每个分数最多变化 ε；最不利时，a 降 ε、j 升 ε，差距仍至少剩下 m − 2ε。

m > 2ε　⇒　m − 2ε > 0

此时 a 仍严格领先所有候选，所以两条路径的贪心选择相同。

反过来不成立。m ≤ 2ε 只是允许选择变化，并非必然变化。bf16 有 95 步满足这个条件，却只有 8 步的贪心选择不同；fp32 没有一步满足，所以这 750 步的贪心选择一致。

合计 8／750，不能告诉我们首次分叉要等多久

这 750 步比较时，两条路径每一步都读取相同的给定历史。8 是选择不同的次数，不是首次分叉时间的分布。要回答首次分叉发生在哪一步，还需要每个问题的首次分叉位置，以及观察结束时仍未分叉的问题。

反例：8 个差异都落在同一题的最后 8 步，或者落在 4 道题各自的前 2 步，都符合 8／750，却有完全不同的首次分叉情况。不能凭这个合计假设各步独立、差异概率恒定。

采样与评测怎样看？

原来的 m 是未加随机性的贪心分差，不能直接保证采样结果相同。一种理解温度 1 采样的方式，是给各候选分数加适当的随机扰动后选最大值；若两条路径使用相同扰动，应在加扰动后的分数上重新计算分差，再使用上述判据。

本样本的采样差异次数为 9，贪心为 8，只能说观察到的次数接近，不能据此证明两者概率相同。随机条件不同时，单次文字差异还混入采样随机性；应另做分布层面的比较。

大王 · 问题 5 参考解析

从第二层起，同一个 token 的 K/V 可以受此前全部可见内容影响。改接到内容不同的前文后，依赖已经变了；前文长度也不同时，位置也变了。相同的文档 token，并不足以使这些 K/V 仍然可用。

等长错误拼接的 KL 为 3.1e-2，约是合法前缀缓存 5.8e-8 的 50 万倍；最可能的 token 仍相同，不能证明拼接正确。

缓存身份必须涵盖会改变计算的条件：完整前缀、位置规则、权重版本、数值精度，以及适用的 LoRA、图片内容等。图片的占位 token 一样，并不代表图片一样。

不必使用链式 hash。完整前缀 hash，或沿前缀树逐 token 匹配，也可以表达完整依赖身份。链式 hash 方便在原编号上增量加入一块，并让不同请求共享已匹配的块。

租户权限是另一项检查。它规定谁可以共享，不决定数值是否兼容；即使计算状态相同，也不代表不同用户有权共用。

压力测试分别检查三件事
  • 计算正确性：与相同请求、相同计算条件下的无压力结果比较 logits，不能只看输出文字。正常数值差异应由合法缓存与分段计算的对照解释，不能拿来掩盖读错数据。
  • 数据生命周期：加入去掉计数或改用布尔标记的失败对照，检查测试能否发现仍在使用的页被覆盖。
  • 复用效率：记录淘汰后还剩多少可命中前缀。先删首块的实现仍可正确重算，但命中归零；正确性通过不代表淘汰策略高效。
大王 · 最后归类：分别验收什么？

实验一、二中的正常缓存与非缓存路径，讨论数学等价计算在有限精度下的数值差异。实验三的错误拼接，以及实验四共享页被覆盖，属于实现的正确性错误，不能用浮点误差解释。有界重放等主动改变恢复计算的方案，属于有意近似，需要另外评价任务质量代价。

因此，输出文字大多没变，不代表没有读错数据；命中率差，也不一定意味着计算错误。正确性、数据生命周期与复用效率要分别验收。

题三

存得下、读得动，能从哪里恢复？

小王要为长对话保存状态。他发现：有的方案保存量小了，却仍被多个层反复读取；有的最终状态很小，却不能直接回到资料结束的地方。下面只比较三个教学配置，不对应某个真实模型。

先固定这次比较的条件

每个会话已处理完 4,096 个 token：前 3,072 个是资料，后 1,024 个是旧问题。模型均为 32 层，所有状态数值用 fp16，每个数 2 字节。1 KiB＝1,024 字节，1 MiB＝1,024 KiB。

扣除模型权重、工作区和管理开销后，实际留给这些会话状态的预算为 640 MiB；按会话保存，不跨会话共享。不另计原文、页表、索引或临时张量；原始 token 保存在别处，可供重放。这里没有额外的压缩器状态。

题设 · 三种独立的教学配置
方案保留哪些状态每层下一步读取什么
A · 完整历史 K/V32 层各存一份完整 K/V；每个 token 的 K、V 各有 2 个头，每头 64 个数。每层读取自己全部 4,096 个历史 token 的 K/V，各读一次。
B · 共享全局＋局部窗口32 层分 4 组，每组 8 层，共用一份全局 K/V；每个 token 的 K、V 形状同 A。每层另有独立的 128-token 局部窗口，K、V 形状也同 A。每层完整读取本组的全局 K/V，再读取自己的 128-token 窗口。两份内容分别计算，不合并读取。
C · 固定大小的递归状态32 层各保留一个 64×256 的数字矩阵；每读入一个 token，就用当前矩阵与本层输入更新它。每层把自己的整个矩阵读一次，再产生更新后的矩阵；不读取逐 token 历史 K/V。

三种方案都只留下表中所说的状态，没有资料末尾的额外快照。B 的全局 K/V 与局部 K/V 是不同状态；全局保存全部 4,096 个位置，各层局部只剩末尾 128 个。本题窗口长度指 128 个旧 token，不含本步新 token；每步先读旧状态，再追加和更新。C 只保存最终矩阵；初始矩阵均为零，可按规则重建，不另占每会话预算。题设没有提供逆向或回退算法。

状态更新是确定的，允许按相同计算路径从初始状态重放来恢复。B 另有一种可选短段办法：只重放资料末尾 128 个 token，并截断这段之前的局部依赖；它接受近似，不能保证还原原状态。

大王 · 问题 1：保存量与容量上限

先算一个 token 在一层的一对 K/V：K 和 V 两份，各有 2×64 个数，每个数 2 字节，共 512 字节。因此 4,096 个 token 占 2 MiB，128 个 token 的窗口占 64 KiB。

问题 1 · 每个会话的保存量与容量上限
方案保存量640 MiB 最多容纳
A每层 2 MiB；32 层共 64 MiB10 个相同长度的会话
B4 份全局共 8 MiB；32 个局部窗口共 2 MiB；合计 10 MiB64 个会话
C每层矩阵 32 KiB；32 层共 1 MiB640 个会话

A 的全部历史、B 的全局部分随 token 数增长；B 的窗口填满后保持固定大小，C 的矩阵大小始终固定。这里的 10、64、640 只是相同长度、只按容量算出的上限，不是能同时满足响应延迟的请求数；继续生成后，增长的状态也会占用更多空间。

大王 · 问题 2：存一份，可能被读取多次
问题 2 · 一步中读取旧状态的逻辑总量
方案怎样相加逻辑读取量
A32 层各读 2 MiB 历史64 MiB／步
B32 层各读 2 MiB 共享全局；再各读 64 KiB 局部窗口66 MiB／步

B 只存四套全局 K/V，但每套被组内八层读取，所以不能用保存的 8 MiB 代替每步的全局读取量。在这个题设中，B 比 A 少存很多，逻辑读取反而多了局部窗口的 2 MiB。

逻辑读取量是按各层“需要读几次”相加；实际硬件可能从更近的缓存复用数据，也可能因分块、布局和搬运产生额外流量。没有给出有效带宽、执行效率和排队条件，就不能把这些数字换成生成速度。

大王 · 问题 3：恢复到资料末尾

现在要接入的是已经给定的新问题，不是先预测资料后的第一个 token；因此这里检查继续读入新输入需要的状态，不额外要求保存资料末尾的词表分数。

问题 3 · 从资料末尾改接新问题
方案现在能从哪里继续哪个快照会改变结论
A各层前 3,072 个 token 的 K/V 仍在。取出这段前缀，丢开旧问题的后缀，即可接入新问题。不缺额外的中间快照；题设已保留完整历史。
B资料的全局 K/V 仍在，但各层窗口只剩旧问题末尾的 3,969～4,096，缺资料末尾的局部状态。需补算。保存处理完 token 3,072 时全部 32 层的局部窗口，合计 2 MiB；配合已保留的全局前缀即可恢复。
C只剩处理完 token 4,096 的矩阵；没有题设允许的回退办法。可从初始矩阵顺序重放资料的 3,072 个 token。保存 token 3,072 之后全部 32 层的矩阵快照，合计 1 MiB；加载后接新问题。

B 没有快照时，可以从初始状态按原路径重放资料，精确补回局部状态。只重放尾部 128 个的可选办法更省计算，却截断了早先依赖，属于有意近似。C 的最终矩阵不能按本题给定的操作拆成任意前缀状态；这不等于所有递归结构在数学上都绝对不可逆。

这里“精确恢复”要求恢复继续计算应有的状态，不能只看最后文字是否相同。保存历史、补算缺失状态、接受近似，是三种不同选择。

#!/usr/bin/env python3
"""Four sequential Claude API requests; running this file incurs API charges."""
import argparse
import getpass
import json
import os
from pathlib import Path
import sys
import time
import urllib.error
import urllib.request
import uuid


def request_once(case, prefix, question, model, api_key):
    payload = {
        "model": model,
        "max_tokens": 96,
        "stream": True,
        "system": [{"type": "text", "text": prefix,
                    "cache_control": {"type": "ephemeral"}}],
        "messages": [{"role": "user", "content": question}],
    }
    request = urllib.request.Request(
        "https://api.anthropic.com/v1/messages",
        data=json.dumps(payload, ensure_ascii=False).encode("utf-8"),
        headers={"content-type": "application/json", "x-api-key": api_key,
                 "anthropic-version": "2023-06-01"},
        method="POST",
    )
    started = time.perf_counter()
    first_text = None
    usage = {}
    complete = False
    error = None
    response_model = None
    stop_reason = None
    try:
        with urllib.request.urlopen(request, timeout=180) as response:
            for line in response:
                if not line.startswith(b"data:"):
                    continue
                event = json.loads(line[5:].strip())
                kind = event.get("type")
                if kind == "message_start":
                    message = event["message"]
                    usage.update(message.get("usage", {}))
                    response_model = message.get("model")
                elif kind == "message_delta":
                    # Output usage is cumulative: replace it, do not add it again.
                    usage.update(event.get("usage", {}))
                    stop_reason = event.get("delta", {}).get("stop_reason")
                elif kind == "content_block_delta":
                    delta = event.get("delta", {})
                    if delta.get("type") == "text_delta" and delta.get("text"):
                        if first_text is None:
                            first_text = time.perf_counter() - started
                elif kind == "error":
                    error = event.get("error", {}).get("type", "stream_error")
                    break
                elif kind == "message_stop":
                    complete = True
                    break
    except urllib.error.HTTPError as exc:
        error = f"HTTP {exc.code}"
    except (OSError, ValueError) as exc:
        error = type(exc).__name__
    if not complete and error is None:
        error = "stream_ended_without_message_stop"
    inputs = [usage.get(k) for k in (
        "input_tokens", "cache_read_input_tokens", "cache_creation_input_tokens")]
    return {
        "case": case, "requested_model": model, "response_model": response_model,
        "first_text_s": round(first_text, 3) if first_text is not None else None,
        "request_s": round(time.perf_counter() - started, 3),
        "total_input_tokens": sum(inputs) if all(type(v) is int for v in inputs) else None,
        "usage": usage, "stop_reason": stop_reason,
        "complete": complete, "error": error,
    }


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("document", help="UTF-8 public reference text")
    parser.add_argument("--model", required=True, help="An available Claude model ID")
    args = parser.parse_args()
    document = Path(args.document).read_text(encoding="utf-8")
    if not document.strip():
        parser.error("The reference text is empty.")
    api_key = os.environ.get("ANTHROPIC_API_KEY") or getpass.getpass("API Key: ")
    if not api_key.strip():
        parser.error("An API key is required.")
    run_id = uuid.uuid4().hex
    prefix = f"实验标识：{run_id}\n材料版本：A\n请依据以下资料回答问题。\n{document}"
    changed = prefix.replace("材料版本：A", "材料版本：B", 1)
    cases = [
        ("1_prepare", prefix, "用一句话概括这份资料。"),
        ("2_confirm", prefix, "用一句话概括这份资料。"),
        ("3_new_question", prefix, "列出这份资料的三个要点。"),
        ("4_changed_prefix", changed, "列出这份资料的三个要点。"),
    ]
    for case, material, question in cases:
        result = request_once(case, material, question, args.model, api_key)
        print(json.dumps(result, ensure_ascii=False), flush=True)
        if not result["complete"]:
            print("请求未完整结束，已停止；已知用量保留在记录中，不自动重试。", file=sys.stderr)

#!/usr/bin/env python3
"""Small, offline KV-cache laboratory. This is NOT a pretrained language model.

Run: python kv_lab.py --output results.json
Requires Python >=3.10 and NumPy. No downloads, credentials, or API requests.
The model is a randomly initialized, 3-layer causal decoder with GQA and RoPE.
Its purpose is to test state reuse, not language ability or production speed.
"""
from __future__ import annotations

import argparse
import hashlib
import json
import math
import platform
import sys
from collections import OrderedDict
from dataclasses import dataclass
from pathlib import Path
from typing import Any

import numpy as np

Array = np.ndarray
State = list[tuple[Array, Array]]


def softmax(x: Array) -> Array:
    e = np.exp(x - x.max(axis=-1, keepdims=True))
    return e / e.sum(axis=-1, keepdims=True)


def rmsnorm(x: Array) -> Array:
    return x / np.sqrt(np.mean(x * x, axis=-1, keepdims=True) + 1e-6)


def rotate(x: Array, positions: Array) -> Array:
    """x: [heads, tokens, head_dim]; interleaved even/odd RoPE pairs."""
    d = x.shape[-1]
    freq = 10000.0 ** (-np.arange(0, d, 2, dtype=np.float64) / d)
    angles = positions[:, None] * freq[None, :]
    c, s = np.cos(angles).astype(x.dtype), np.sin(angles).astype(x.dtype)
    y = np.empty_like(x)
    y[..., 0::2] = x[..., 0::2] * c - x[..., 1::2] * s
    y[..., 1::2] = x[..., 0::2] * s + x[..., 1::2] * c
    return y


@dataclass(frozen=True)
class Config:
    vocab: int = 41
    width: int = 32
    layers: int = 3
    q_heads: int = 4
    kv_heads: int = 2
    head_dim: int = 8
    seed: int = 7
    dtype: str = "float64"


class TinyDecoder:
    def __init__(self, cfg: Config = Config()):
        if (cfg.width != cfg.q_heads * cfg.head_dim or
            cfg.q_heads % cfg.kv_heads or cfg.head_dim % 2):
            raise ValueError("Invalid head dimensions or GQA grouping")
        self.cfg = cfg
        dtype = np.dtype(cfg.dtype)
        if dtype not in (np.dtype('float32'), np.dtype('float64')):
            raise ValueError("This lab supports float32 and float64 only")
        rng = np.random.default_rng(cfg.seed)
        self.embed = (rng.normal(size=(cfg.vocab, cfg.width)) * 0.3).astype(dtype)
        shapes = [(cfg.width, cfg.q_heads * cfg.head_dim),
                  (cfg.width, cfg.kv_heads * cfg.head_dim),
                  (cfg.width, cfg.kv_heads * cfg.head_dim),
                  (cfg.width, cfg.width), (cfg.width, cfg.width * 2),
                  (cfg.width * 2, cfg.width)]
        self.weights = [[(rng.normal(size=sh) / math.sqrt(sh[0])).astype(dtype)
                         for sh in shapes] for _ in range(cfg.layers)]
        self.lm_head = (rng.normal(size=(cfg.width, cfg.vocab)) /
                        math.sqrt(cfg.width)).astype(dtype)
        h = hashlib.sha256(json.dumps(cfg.__dict__, sort_keys=True).encode())
        for a in [self.embed, self.lm_head] + [w for row in self.weights for w in row]:
            h.update(a.tobytes())
        # Includes actual weights, not just a model name. RoPE rule is fixed by code.
        self.identity = 'tiny-gqa-rope-v1:' + h.hexdigest()
        self.processed_positions = 0

    def empty_state(self) -> State:
        c = self.cfg
        return [(np.empty((c.kv_heads, 0, c.head_dim), dtype=c.dtype),
                 np.empty((c.kv_heads, 0, c.head_dim), dtype=c.dtype))
                for _ in range(c.layers)]

    def forward(self, tokens: list[int], past: State | None = None) -> tuple[Array, State]:
        """Processes ONLY tokens supplied here; past has already been computed.

        Token indices in the causal mask are ABSOLUTE, including the cached offset.
        This function returns new arrays; it never mutates a supplied cache.
        """
        c = self.cfg
        if not tokens or any(type(t) is not int or not 0 <= t < c.vocab for t in tokens):
            raise ValueError("Provide a nonempty list of integer IDs within the vocabulary")
        past = self.empty_state() if past is None else past
        if len(past) != c.layers:
            raise ValueError("Cache layer count mismatch")
        start = past[0][0].shape[1]
        for k, v in past:
            expected = (c.kv_heads, start, c.head_dim)
            if k.shape != expected or v.shape != expected:
                raise ValueError("Inconsistent cache shapes")
            if k.dtype != np.dtype(c.dtype) or v.dtype != np.dtype(c.dtype):
                raise ValueError("Cache dtype mismatch")
        pos = np.arange(start, start + len(tokens))
        x = self.embed[tokens].copy()
        out_state = []
        self.processed_positions += len(tokens)
        for layer, (wq, wk, wv, wo, w1, w2) in enumerate(self.weights):
            h = rmsnorm(x)
            q = (h @ wq).reshape(-1, c.q_heads, c.head_dim).transpose(1, 0, 2)
            k = (h @ wk).reshape(-1, c.kv_heads, c.head_dim).transpose(1, 0, 2)
            v = (h @ wv).reshape(-1, c.kv_heads, c.head_dim).transpose(1, 0, 2)
            q, k = rotate(q, pos), rotate(k, pos)
            k = np.concatenate([past[layer][0], k], axis=1)
            v = np.concatenate([past[layer][1], v], axis=1)
            out_state.append((k, v))  # Persist KV heads, not repeated Q heads.
            kr = np.repeat(k, c.q_heads // c.kv_heads, axis=0)
            vr = np.repeat(v, c.q_heads // c.kv_heads, axis=0)
            scores = (q @ kr.transpose(0, 2, 1)) / math.sqrt(c.head_dim)
            allowed = np.arange(k.shape[1])[None, :] <= pos[:, None]
            scores = np.where(allowed[None, :, :], scores, -np.inf)
            a = (softmax(scores) @ vr).transpose(1, 0, 2).reshape(-1, c.width)
            x = x + a @ wo
            z = rmsnorm(x) @ w1
            x = x + (z / (1 + np.exp(-z))) @ w2
        return rmsnorm(x) @ self.lm_head, out_state


@dataclass
class Entry:
    tokens: tuple[int, ...]  # Collision guard; each entry stores a full block only.
    state: State            # This block's K/V across all layers, never a whole prefix.


class PrefixCache:
    """Serial educational prefix cache. Hits are copied before model execution.

    Source blocks cannot be evicted midway because this implementation is serial.
    Production async transfers need ownership protection until the copy completes.
    This class stores neither final logits nor hidden states, so it leaves >=1 input.
    """
    def __init__(self, model: TinyDecoder, block_size: int = 16,
                 capacity_blocks: int = 128, namespace: str = "local-demo"):
        if block_size < 1 or capacity_blocks < 1:
            raise ValueError("Block size and capacity must be positive")
        self.model = model
        self.block_size = block_size
        self.capacity = capacity_blocks
        self.base = hashlib.sha256((model.identity + ':' + namespace).encode()).digest()
        self.blocks: OrderedDict[bytes, Entry] = OrderedDict()

    def keys(self, tokens: list[int]):
        parent = self.base
        b = self.block_size
        for end in range(b, len(tokens) + 1, b):
            block = tuple(tokens[end-b:end])
            raw = np.asarray(block, dtype='<i8').tobytes()
            key = hashlib.sha256(parent + raw).digest()
            yield end, key, block
            parent = key

    def lookup(self, tokens: list[int]) -> tuple[int, State | None]:
        rows: list[State] = []
        hit = 0
        for end, key, block in self.keys(tokens):
            if end >= len(tokens):
                break  # Need a final hidden state, not only K/V.
            entry = self.blocks.get(key)
            if entry is None or entry.tokens != block:
                break
            self.blocks.move_to_end(key)
            rows.append(entry.state)
            hit = end
        if not rows:
            return 0, None
        state = [(np.concatenate([r[i][0] for r in rows], axis=1).copy(),
                  np.concatenate([r[i][1] for r in rows], axis=1).copy())
                 for i in range(self.model.cfg.layers)]
        return hit, state

    def store(self, tokens: list[int], state: State) -> None:
        # Reverse insertion makes the beginning newer than the tail in this toy LRU.
        # It preserves a useful prefix when one old block must be evicted.
        for end, key, block in reversed(list(self.keys(tokens))):
            if key not in self.blocks:
                if len(self.blocks) >= self.capacity:
                    self.blocks.popitem(last=False)
                sliced = [(k[:, end-self.block_size:end].copy(),
                           v[:, end-self.block_size:end].copy()) for k, v in state]
                self.blocks[key] = Entry(block, sliced)
            self.blocks.move_to_end(key)

    def request(self, tokens: list[int]) -> tuple[Array, State, dict[str, int]]:
        hit, state = self.lookup(tokens)
        logits, state = self.model.forward(tokens[hit:], state)
        self.store(tokens, state)
        return logits[-1], state, {"input_tokens": len(tokens), "hit_tokens": hit,
                                   "computed_tokens": len(tokens)-hit}


def online_attention(q: Array, k: Array, v: Array, block: int = 7) -> Array:
    """One query, all keys visible. Online global softmax; not a GPU kernel."""
    m = -np.inf
    l = 0.0
    acc = np.zeros(v.shape[-1], dtype=np.float64)
    for i in range(0, len(k), block):
        s = k[i:i+block] @ q / math.sqrt(q.size)
        new_m = max(m, float(s.max()))
        alpha = math.exp(m-new_m)
        p = np.exp(s-new_m)
        acc = alpha * acc + p @ v[i:i+block]
        l = alpha * l + float(p.sum())
        m = new_m
    return acc / l


def pack_int4(x: Array, group: int = 16) -> tuple[Array, Array, tuple[int, ...]]:
    """Uniform signed INT4, NOT NVFP4. One FP32 scale per group, no zero point.
    Codes use [-7,7]; +8 offset enables two codes per uint8. Pad zeros at the tail.
    """
    if group < 2 or group % 2:
        raise ValueError("Group must be positive and even")
    f = np.asarray(x, dtype=np.float32).reshape(-1)
    if not np.isfinite(f).all():
        raise ValueError("Quantization requires finite input")
    n = ((len(f) + group - 1) // group) * group
    a = np.pad(f, (0, n-len(f))).reshape(-1, group)
    scales = np.max(np.abs(a), axis=1).astype(np.float32) / 7
    scales[scales == 0] = 1
    codes = (np.rint(a / scales[:, None]).clip(-7, 7).astype(np.int8) + 8).astype(np.uint8)
    codes = codes.reshape(-1)
    packed = codes[0::2] | (codes[1::2] << 4)
    return packed, scales, x.shape


def unpack_int4(packed: Array, scales: Array, shape: tuple[int, ...], group: int = 16) -> Array:
    codes = np.empty(packed.size * 2, dtype=np.int16)
    codes[0::2] = packed & 15
    codes[1::2] = packed >> 4
    a = ((codes - 8).reshape(-1, group) * scales[:, None]).reshape(-1)
    return a[:math.prod(shape)].reshape(shape)


class PagePool:
    """Small single-threaded page-ownership simulation (not model execution)."""
    def __init__(self, capacity: int = 4):
        self.capacity = capacity
        self.pages: dict[int, Array] = {}
        self.refs: dict[int, int] = {}

    def allocate(self, data: Array) -> int:
        for p in range(self.capacity):
            if self.refs.get(p, 0) == 0:
                self.pages[p] = data.copy()
                self.refs[p] = 1
                return p
        raise MemoryError("All pages are held by readers")

    def retain(self, p: int) -> None:
        if self.refs.get(p, 0) <= 0:
            raise RuntimeError("Cannot retain a free page")
        self.refs[p] += 1

    def release(self, p: int) -> None:
        if self.refs.get(p, 0) <= 0:
            raise RuntimeError("Double release or unknown page")
        self.refs[p] -= 1

    def private_for_write(self, p: int) -> int:
        if self.refs.get(p, 0) <= 0:
            raise RuntimeError("Cannot write a free page")
        if self.refs[p] == 1:
            return p
        # Allocate before dropping the old reference, so failure is safe.
        new_p = self.allocate(self.pages[p])
        self.release(p)
        return new_p


def max_error(a: Array, b: Array) -> float:
    return float(np.max(np.abs(a-b)))

# KV 缓存最小实验：先把状态复用做出来

这是补充教材的可运行伴随实验，版本 1.0，整理于 2026-10-09。

## 跑什么

`kv_lab.py` 从固定随机种子构建三层因果 Transformer：4 个 Q 头、2 个 KV 头、每头 8 维、RoPE、RMSNorm、前馈层和词表输出。词表为 41 个整数 ID，无分词器、外部数据集、模型下载或付费 API。

需要 Python 3.10 及以上。本次验证环境是 Python 3.13.5、NumPy 2.3.5、CPU。

## 先预测，再看结果

1. 两个输入共享前 42 个 token，缓存以 16 token 为单位，只保存整块。第二个输入共 47 token。命中 32，重算 15；不是共享的 42 都能复用。
2. “不查表，只把输入分两段计算”是必要对照：它能分离分段执行带来的数值差异与缓存管理错误。
3. 把文档的旧 K/V 接到长度相同、内容不同的前文后，位置不变仍然可能错。重放文档是精确修复对照；本实验**没有实现 CacheBlend**。
4. `PagePool` 中先让两个使用者共享一页，再结束其中一个；另一人没结束之前，不能覆盖。写共享尾页之前先复制。
